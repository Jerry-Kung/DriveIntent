# “线索获客”项目总体设计文档

**文档版本：** V0.1
**项目阶段：** MVP探索与初步验证
**项目暂定名称：** 线索获客
**核心应用场景：** 短视频平台汽车评论潜客识别
**建设原则：** 小步快跑、AI优先、证据驱动、逻辑分层、轻量实现、可持续扩展

------

## 1. 项目概述

### 1.1 项目背景

抖音、TikTok等短视频平台已经成为汽车品牌宣传、车型测评、用户交流和购车决策的重要内容渠道。

在车企官方账号、汽车媒体账号、汽车博主账号及客户自营账号发布的视频下，存在大量用户评论。这些评论中不仅包含普通互动、情绪表达和娱乐内容，也包含一部分具有真实业务价值的购车需求，例如：

- 询问价格、优惠和落地成本；
- 询问置换补贴和金融政策；
- 咨询门店、试驾和车辆交付；
- 对比不同品牌或车型；
- 讨论配置、空间、续航、油耗和养车成本；
- 表达明确或潜在的购车、换车计划。

当前这些潜在线索通常散落在海量评论中，主要依赖人工查看，存在效率低、覆盖范围有限、判断标准不一致等问题。

“线索获客”项目希望利用大语言模型对视频、评论和用户公开主页信息进行综合分析，从海量评论中筛选具有真实购车意向的用户，并将其转化为车企销售人员可以直接跟进的结构化销售线索。

------

### 1.2 项目定位

本项目不是简单的评论情感分析系统，也不是寻找“对车辆表达正面态度”的用户。

项目的核心定位是：

> 基于短视频语境、评论内容和用户公开行为证据，识别真实购车需求，将公域平台中的潜在用户转化为可解释、可验证、可跟进的销售线索。

系统需要区分以下几类概念：

1. **正面情绪**

   例如“好看”“厉害”“good”，只能说明用户态度，不能说明用户有购车计划。

2. **汽车或产品兴趣**

   例如“这个内饰不错”“颜色很好看”，说明用户对产品有一定兴趣，但不代表其已经进入购车决策阶段。

3. **潜在购车需求**

   例如“这款和XX相比怎么样”“后期保养贵不贵”，说明用户可能已经开始了解或比较车型。

4. **明确购车意向**

   例如“上海落地多少钱”“旧车置换有补贴吗”“哪里可以试驾”，说明用户已经接近实际交易或行动阶段。

项目最终关注的是第三类和第四类用户，尤其是具有明确购车决策和行动信号的高意向用户。

------

### 1.3 数据边界

项目所需的短视频、评论及用户公开主页信息，由车企客户通过合法的第三方数据渠道提供。

本项目不负责：

- 短视频平台数据抓取；
- 绕过平台权限限制；
- 非公开数据获取；
- 用户隐私数据采集。

本项目主要负责：

- 数据接收与标准化；
- 视频与评论语义分析；
- 潜在购车意向识别；
- 用户级意向聚合；
- 线索分级；
- 购车意向画像；
- 销售线索结果输出。

------

## 2. 项目目标

### 2.1 当前阶段核心目标

当前项目处于探索和业务可行性验证阶段，首期目标不是建设完整的平台化系统，而是：

> 在一周左右完成一个可以端到端运行的MVP版本，验证短视频评论数据能否稳定产出具有业务价值的购车线索。

MVP需要回答以下核心问题：

1. 能否有效过滤无意义、情绪化和明显营销类评论；
2. 能否从评论中识别真实购车意向；
3. 能否通过用户多条评论和公开主页信息提升判断准确性；
4. 能否将用户划分为合理的H/A/B/C意向等级；
5. 能否生成销售人员可以理解和使用的线索卡片；
6. 线索结果是否能够得到业务人员的人工认可。

------

### 2.2 中长期扩展目标

MVP验证成功后，系统可以逐步扩展以下能力：

- 产品优缺点分析；
- 品牌及车型口碑分析；
- 竞品比较分析；
- 用户需求趋势分析；
- 舆情监控和风险告警；
- 高价值评论实时发现；
- 营销内容效果分析；
- 销售私信策略生成；
- 线索跟进与转化效果分析。

因此，首期设计既要足够轻量，也不能将未来扩展路径封死。

------

## 3. 总体设计原则

### 3.1 小步快跑

首期只建设当前业务验证所需的最小能力，不提前建设复杂平台。

暂不建设：

- 通用规则引擎；
- 通用Agent平台；
- Kafka事件总线；
- 实时流计算平台；
- 特征平台；
- 通用DAG编排平台；
- 多微服务体系；
- 模型训练平台；
- 在线自动学习系统；
- 完整舆情告警平台。

------

### 3.2 逻辑分层，物理合并

系统在逻辑上保持清晰的L1—L5五层结构，但MVP阶段不将每一层拆分成独立服务。

首期采用模块化单体架构：

- 一个后端应用；
- 一个关系型数据库；
- 一个LLM调用网关；
- 一套Skill配置；
- 一条固定分析工作流；
- 一个简单业务展示界面。

逻辑边界用于保证代码可维护和未来可拆分，物理合并用于降低建设成本。

------

### 3.3 LLM Skill优先

对于语义理解、复杂判断和业务逻辑，优先通过LLM Prompt Skill完成。

适合交给LLM的任务包括：

- 视频语境理解；
- 评论是否有实际业务价值；
- 评论是否表达购车需求；
- 评论是否疑似营销或水军内容；
- 用户购车阶段判断；
- 购车需求、痛点和顾虑提取；
- H/A/B/C分级；
- 销售沟通切入点生成。

仅在以下情况下使用确定性代码或算法：

- 数据格式转换；
- ID去重；
- 用户评论聚合；
- 数量和时间统计；
- 任务状态管理；
- JSON Schema校验；
- 聚类、向量相似度等LLM不擅长的计算任务。

------

### 3.4 确定性工作流与专业化Skill结合

MVP不采用完全自主规划的多Agent架构，而采用：

> 确定性工作流控制执行顺序，专业化LLM Skill负责语义理解与业务判断。

这种方式兼顾了AI能力和工程稳定性：

- 工作流可预测；
- 输入输出结构明确；
- 调试和评测容易；
- Token成本可控制；
- 问题可以定位到具体Skill；
- Skill可以独立升级和回归测试。

------

### 3.5 证据驱动

所有购车意向、用户画像和线索等级必须能够回溯到原始证据。

系统不得仅输出结论，还需要记录：

- 结论对应的评论；
- 评论所在的视频；
- 相关用户公开信息；
- 判断理由；
- 置信度；
- 使用的Skill版本；
- 使用的模型和Prompt版本。

------

### 3.6 原始数据与分析结果分离

原始数据保留不变，分析结果允许重新生成。

当以下内容发生变化时：

- Prompt更新；
- Skill逻辑调整；
- 模型更换；
- 分级标准变化；
- 客户增加新的判断原则；

系统可以直接对历史数据重新分析，而不需要重新获取数据。

------

### 3.7 先保证准确率，再追求召回率

销售人员能够处理的线索数量有限。

如果系统输出大量无效H/A级线索，会迅速降低业务人员对系统的信任。

MVP阶段应优先保证：

- H级线索准确率；
- H/A级线索整体准确率；
- 无效评论过滤效果；
- 疑似营销评论识别效果。

在准确率达到业务可接受水平后，再逐步提升召回率。

------

## 4. 总体架构

系统采用五层逻辑架构：

```text
L5 业务应用层
线索列表、线索详情、人工审核、数据导出

L4 业务策略层
用户有效性判断、H/A/B/C分级、线索摘要、销售建议

L3 AI分析能力层
视频语境Skill、评论筛选Skill、用户综合分析Skill

L2 事实与特征层
视频语境结果、评论意向结果、用户聚合结果、简单统计特征

L1 数据与证据层
视频、评论、用户基础信息、用户公开主页、原始数据
```

横向提供少量公共能力：

- LLM调用封装；
- Skill配置加载；
- Prompt版本管理；
- JSON Schema校验；
- 任务状态管理；
- 自动重试；
- 日志和错误记录。

------

## 5. 各层详细设计

# 5.1 L1：数据与证据层

### 5.1.1 核心职责

L1负责接收、标准化和保存客户提供的原始数据。

主要职责包括：

- 接收视频数据；
- 接收评论数据；
- 接收用户公开主页数据；
- 统一不同平台的数据格式；
- 为数据分配稳定ID；
- 保存原始第三方数据；
- 支持重复导入和幂等处理；
- 为后续分析提供证据引用。

------

### 5.1.2 核心数据对象

MVP阶段保留以下核心对象。

#### Video：视频

主要字段：

- 平台；
- 视频ID；
- 发布账号；
- 账号类型；
- 视频标题；
- 视频文案；
- 话题标签；
- 视频发布时间；
- 视频文本转写或摘要；
- 品牌和车型基础信息；
- 原始数据；
- 数据导入时间。

#### Comment：评论

主要字段：

- 平台；
- 评论ID；
- 视频ID；
- 用户ID；
- 原始评论文本；
- 评论时间；
- 点赞数；
- 回复数；
- 是否为回复评论；
- 原始数据；
- 数据导入时间。

#### PlatformUser：平台用户

主要字段：

- 平台；
- 用户ID；
- 昵称；
- 头像地址；
- 用户简介；
- 地区信息；
- 账号基础信息。

#### UserProfileSnapshot：用户公开主页快照

主要字段：

- 用户ID；
- 采集时间；
- 用户公开简介；
- 公开历史视频；
- 公开内容摘要；

- 原始主页数据。

主要字段：

- 分析对象类型；
- 分析对象ID；
- Skill ID；
- Skill版本；
- 模型名称；
- Prompt版本；
- 分析状态；
- 结果JSON；
- 置信度；
- 创建时间；
- 错误信息。

#### Lead：业务线索

主要字段：

- 用户ID；
- 当前线索等级；
- 线索状态；
- 目标品牌和车型；
- 线索摘要；
- 购车阶段；
- 核心需求；
- 主要顾虑；
- 推荐销售切入点；
- 证据评论；
- 置信度；
- 人工审核结果；
- 创建和更新时间。

------

### 5.1.3 数据设计原则

#### 原始数据不可覆盖

第三方传入的原始JSON需要完整保存，便于：

- 问题排查；
- 数据核对；
- 数据格式升级；
- 历史重新分析。

#### 分析结果允许多版本并存

同一个评论或用户可以保留多个不同Skill版本的分析结果。

例如：

```text
comment_001
├── comment_lead_screening_v1.0
├── comment_lead_screening_v1.1
└── comment_lead_screening_v2.0
```

业务默认读取当前生效版本，但历史结果不能直接覆盖。

# 5.2 L2：事实与特征层

### 5.2.1 核心职责

L2负责保存AI分析产生的结构化结果，以及由普通代码计算得到的简单统计特征。

MVP阶段不建设复杂的Fact平台和Feature Store，而采用：

> 统一分析结果表，加各Skill独立的结构化JSON Schema。

------

### 5.2.2 视频语境结果

视频语境结果用于帮助评论分析理解评论所处的上下文。

示例：

```json
{
  "brand": "品牌A",
  "model": "车型A",
  "content_type": "新车发布",
  "main_topics": [
    "价格",
    "空间",
    "智能座舱"
  ],
  "target_audience": "家庭用户",
  "competitor_models": [
    "竞品车型B"
  ],
  "commercial_context": "车企官方宣传",
  "analysis_notes": "评论中涉及价格、配置和购买计划的内容需要重点关注"
}
```

------

### 5.2.3 评论筛选结果

每条评论需要输出以下信息：

- 是否有意义；
- 是否与视频或汽车相关；
- 是否可能表达购车需求；
- 是否疑似营销或水军；
- 购车意向信号；
- 目标品牌；
- 目标车型；
- 初步意向强度；
- 判断理由；
- 置信度。

示例：

```json
{
  "comment_id": "comment_001",
  "is_meaningful": true,
  "is_automotive_related": true,
  "is_purchase_related": true,
  "is_suspected_marketing": false,
  "intent_signals": [
    "price_inquiry",
    "trade_in"
  ],
  "target_brand": "品牌A",
  "target_model": "车型A",
  "intent_strength": "high",
  "reason": "用户询问落地价格和旧车置换政策，具有明确交易意向",
  "confidence": 0.94
}
```

------

### 5.2.4 用户聚合结果

由普通代码按平台用户ID聚合：

- 用户有效评论；
- 评论所在视频；
- 评论时间范围；
- 相关品牌和车型；
- 有效评论数量；
- 初步高意向评论数量；
- 重复评论数量；
- 用户主页信息。

示例：

```json
{
  "user_id": "user_001",
  "valid_comment_ids": [
    "comment_001",
    "comment_015"
  ],
  "related_video_ids": [
    "video_001",
    "video_006"
  ],
  "simple_statistics": {
    "valid_comment_count": 2,
    "high_intent_comment_count": 1,
    "related_model_count": 2
  }

```

------

### 5.2.5 用户意向分析结果

用户综合分析结果包括：

- H/A/B/C等级；
- 购车阶段；
- 关注品牌车型；
- 核心需求；
- 使用场景；
- 主要顾虑；
- 购车时间；
- 推荐销售切入点；
- 需要销售确认的问题；
- 证据；
- 置信度。

# 5.3 L3：AI分析能力层

### 5.3.1 Skill机制

MVP采用轻量Skill机制封装AI能力。

一个Skill主要包含：

- Skill ID；
- Skill版本；
- 功能说明；
- 输入Schema；
- 输出Schema；
- Prompt模板；
- 模型配置；
- 推理参数；
- Few-shot示例；
- 错误重试策略。

示例：

```yaml
skill_id: comment_lead_screening
version: "1.0"

description: >
  结合视频语境判断评论是否具有真实购车价值，
  并识别无意义评论、营销内容和购车意向信号。

input_schema:
  - video_context
  - comments

output_schema: comment_lead_screening_v1

model:
  name: qwen-local
  temperature: 0.1

prompt_file: prompts/comment_lead_screening_v1.txt
```

------

### 5.3.2 MVP核心Skill

MVP阶段只实现三个核心Skill。

## Skill 1：视频语境理解

### 输入

- 视频标题；
- 视频文案；
- 发布账号类型；
- 话题标签；
- 可选的视频转写；
- 可选的客户预置品牌车型信息。

### 输出

- 品牌和车型；
- 视频内容类型；
- 主要讨论主题；
- 视频目标受众；
- 视频商业属性；
- 竞品信息；
- 评论分析注意事项。

### 调用粒度

每个视频只分析一次，分析结果供该视频下所有评论复用。

------

## Skill 2：评论线索筛选

### 输入

- 视频语境；
- 一批评论；
- 当前线索判断原则。

### 输出

对每条评论分别输出：

- 是否有意义；
- 是否与汽车或视频相关；
- 是否存在购车意向；
- 是否疑似营销或水军；
- 意向信号；
- 目标品牌车型；
- 初步意向强度；
- 判断理由；
- 置信度。

### 处理原则

该Skill必须明确区分：

- 正面情绪；
- 产品兴趣；
- 潜在购车需求；
- 明确交易意向。

同时需要避免以下误判：

- “厉害”“good”等无意义评论；
- 纯粹号召他人购买的营销评论；
- 单纯吹捧；
- 单纯吐槽；
- 玩梗；
- 与视频无关的内容。

但对于包含真实需求的负面表达，不能简单过滤。

例如：

> “我现在这辆车售后太差了，准备换一个品牌。”

虽然情绪偏负面，但包含明显换车需求，属于有价值线索。

### 批量策略

同一视频下的评论建议每批处理20—50条。

优点包括：

- 降低LLM调用成本；
- 提高吞吐量；
- 便于识别同批评论中的模板化表达；
- 避免逐条请求产生大量网络开销。

------

## Skill 3：用户线索综合分析

### 输入

- 用户全部有效候选评论；
- 评论对应的视频语境；
- 用户公开主页信息；
- 用户公开历史内容；
- 简单统计特征；
- H/A/B/C分级标准。

### 输出

- 用户意向等级；
- 线索有效性；
- 购车阶段；
- 目标品牌车型；
- 核心需求；
- 主要痛点；
- 主要顾虑；
- 购车时间；
- 使用场景；
- 推荐沟通切入点；
- 销售需要确认的问题；
- 证据评论；
- 置信度。

### 首期职责边界

首期为了提升开发速度，将以下能力合并在同一Skill中：

- 用户购车意向分析；
- H/A/B/C分级；
- 简单购车意向画像；
- 销售切入点建议。

当业务成熟后，可以根据实际问题再拆分成：

```text
用户意向分析Skill
→ 线索分级Skill
→ 销售策略Skill
```

MVP阶段不提前拆分。

------

### 5.3.3 Skill执行器

Skill执行器负责：

1. 读取Skill配置；
2. 获取上游数据；
3. 根据Prompt模板组装输入；
4. 调用指定LLM；
5. 解析JSON；
6. 校验输出Schema；
7. 对异常结果自动重试；
8. 保存分析结果；
9. 记录模型、Prompt和Skill版本。

Skill执行器不负责决定业务流程，业务流程由固定工作流控制。

------

# 5.4 L4：业务策略层

### 5.4.1 核心职责

L4负责将L2和L3产生的分析结果转化为最终业务结论。

MVP阶段主要包括：

- 判断用户是否形成有效销售线索；
- 输出H/A/B/C等级；
- 生成线索摘要；
- 生成购车意向画像；
- 生成销售切入建议。

------

### 5.4.2 H/A/B/C分级标准

## H级：极高意向

用户已经出现明确交易或行动信号，例如：

- 询问价格或落地价；
- 询问优惠政策；
- 询问置换补贴；
- 询问贷款或金融方案；
- 询问门店、库存或交付；
- 询问试驾；
- 明确表达近期购买或换车计划；
- 在具体配置之间进行最终选择。

示例：

> “上海落地多少钱，最近有优惠吗？”

> “旧车置换这款能补多少？准备年底换车。”

------

## A级：较强意向

用户已经进入主动评估或对比阶段，例如：

- 对比具体竞品；
- 讨论车型优缺点；
- 深入询问配置差异；
- 关注养车成本；
- 关注保值率、售后和质量；
- 讨论真实使用场景；
- 评估购车政策。

示例：

> “这款和竞品A相比，底盘和隔音哪个更好？”

------

## B级：中等意向

用户对产品存在一定兴趣，但尚未进入深度决策，例如：

- 讨论外观或内饰；
- 进行浅层配置咨询；
- 对空间、颜色等感兴趣；
- 表示“有点心动”；
- 表示未来可能考虑。

------

## C级：较低意向

用户与汽车或车型相关，但购车意向较弱，例如：

- 普通吐槽；
- 玩梗；
- 浅层情绪表达；
- 缺乏具体需求和购买计划。

------

### 5.4.3 无效及异常用户处理

虽然最终业务等级为H/A/B/C，但系统内部需要保留以下状态：

- 无意义评论；
- 与汽车无关；
- 无购车意向；
- 疑似营销；
- 疑似水军；
- 信息不足。

这些用户不进入正常销售线索列表，避免污染C级线索池。

MVP阶段不一定需要在前端展示N或S等级，但需要在分析结果中保存对应判断。

------

### 5.4.4 Prompt策略优先

当前不建设独立规则引擎。

当客户增加新的业务判断原则时，优先通过以下方式实现：

1. 修改Skill Prompt；
2. 增加判断原则描述；
3. 增加Few-shot案例；
4. 发布新的Skill版本；
5. 对历史样本重新分析；
6. 对比新旧版本效果。

只有当规则无法被LLM稳定执行，或需要严格数值计算时，才考虑增加确定性代码逻辑。

------

## 6. “线索获客”完整业务流程

### 6.1 流程总览

```text
客户提供视频、评论和用户基础数据
                ↓
L1 数据导入与标准化
                ↓
视频语境理解Skill
                ↓
评论批量筛选Skill
                ↓
候选用户评论聚合
                ↓
获取候选用户公开主页信息
                ↓
用户线索综合分析Skill
                ↓
生成H/A/B/C线索
                ↓
线索列表和详情展示
                ↓
业务人员人工审核
```

------

### 6.2 步骤一：数据导入

系统接收客户提供的：

- 视频信息；
- 视频评论；
- 评论用户基础信息。

数据写入：

- `video`；
- `comment`；
- `platform_user`。

同时保留第三方原始JSON。

系统根据平台和外部ID进行幂等判断，避免重复导入。

------

### 6.3 步骤二：视频语境分析

对每个视频调用一次视频语境理解Skill。

输出视频所属：

- 品牌；
- 车型；
- 内容类型；
- 主要讨论主题；
- 商业属性；
- 竞品关系；
- 评论分析重点。

视频语境结果缓存复用，不对每条评论重复分析视频。

------

### 6.4 步骤三：评论批量筛选

同一视频下的评论按20—50条分批调用评论筛选Skill。

Skill需要识别：

- 无意义评论；
- 与视频无关评论；
- 普通情绪表达；
- 产品兴趣；
- 潜在购车需求；
- 明确购车意向；
- 疑似营销评论；
- 疑似水军评论。

只有满足以下条件的评论进入后续流程：

- 评论有实际信息；
- 评论与汽车或目标视频相关；
- 评论可能包含购车需求；
- 评论不属于明显营销或无效内容。

------

### 6.5 步骤四：用户级聚合

使用普通程序代码按用户ID聚合候选评论。

形成用户证据包：

- 用户全部有效评论；
- 评论所在视频；
- 评论时间；
- 涉及品牌车型；
- 评论意向信号；
- 简单统计数据。

此阶段不需要调用LLM。

------

### 6.6 步骤五：补充用户公开主页信息

只针对通过评论筛选的候选用户获取主页数据。

避免对以下用户请求主页：

- 只有无意义评论；
- 没有购车相关信号；
- 明显营销或水军账号；
- 只有低价值情绪表达。

这种方式可以有效减少数据处理量和LLM调用成本。

------

### 6.7 步骤六：用户综合分析

将以下信息提交给用户线索综合分析Skill：

- 用户有效评论；
- 视频语境；
- 用户公开主页；
- 用户公开历史内容；
- 简单统计特征；
- H/A/B/C判断标准。

Skill输出用户最终线索结果。

示例：

```json
{
  "lead_grade": "H",
  "is_valid_lead": true,
  "confidence": 0.91,
  "lead_summary": "用户近期存在明确换车计划，重点关注车型A的落地价格和置换补贴。",
  "purchase_stage": "交易准备阶段",
  "target_brands": [
    "品牌A"
  ],
  "target_models": [
    "车型A"
  ],
  "core_needs": [
    "家庭空间",
    "旧车置换"
  ],
  "main_concerns": [
    "落地价格"
  ],
  "purchase_time": "近期",
  "recommended_entry_point": "优先从当地置换政策和旧车评估服务切入。",
  "verification_questions": [
    "您当前车辆是什么车型和年限？",
    "预计什么时候完成换车？"
  ],
  "evidence": [
    {
      "comment_id": "comment_001",
      "content": "上海落地多少钱，旧车置换有补贴吗？"
    }
  ]
}
```

------

### 6.8 步骤七：业务输出与人工验证

最终线索写入`lead`表。

业务人员可以：

- 查看H/A/B/C线索；
- 查看线索依据；
- 查看用户购车意向画像；
- 导出线索列表；
- 对结果进行人工审核；
- 将高意向用户交给销售人员进行私信沟通。

## 7. MVP物理架构

MVP采用模块化单体架构。

```text
第三方数据文件或API
          ↓
模块化单体后端应用
├── Data Importer
├── Workflow Runner
├── Skill Executor
├── LLM Gateway
├── Lead Service
└── Query / Export API
          ↓
PostgreSQL
├── 原始数据
├── 分析任务
├── 分析结果
└── 销售线索
          ↑
简单管理页面或现有前端系统
```

------

### 7.1 推荐技术实现

后端可采用：

- Python；
- FastAPI；
- SQLAlchemy；
- Pydantic；
- PostgreSQL。

异步任务首期可采用：

> 数据库任务表＋后台Worker。

暂时无需引入：

- Kafka；
- RabbitMQ；
- Redis；
- Celery；
- 专用工作流平台。

当后续任务量和并发量明显增加时，再评估引入专业消息队列或任务框架。

------

## 8. 高可用与稳定性设计

MVP不建设复杂集群，但需要保证任务可以恢复和重试。

### 8.1 幂等处理

分析任务使用以下组合形成幂等键：

```text
分析对象ID
＋ Skill ID
＋ Skill版本
```

相同对象和相同Skill版本不重复执行。

------

### 8.2 任务状态

任务状态至少包括：

- `pending`：等待执行；
- `running`：正在执行；
- `success`：执行成功；
- `failed`：执行失败。

------

### 8.3 自动重试

以下情况自动重试2—3次：

- LLM接口超时；
- 网络异常；
- JSON解析失败；
- 输出不符合Schema；
- 模型返回空内容。

多次失败后记录错误原因，并支持人工重新执行。

------

### 8.4 分阶段保存

三个核心Skill结果分别保存：

- 视频分析结果；
- 评论分析结果；
- 用户分析结果。

用户分析失败时，无需重新执行视频和评论分析。

------

### 8.5 Schema校验

所有LLM输出必须通过Pydantic或JSON Schema校验。

对于不合格输出：

1. 自动尝试修复；
2. 修复失败后重新调用；
3. 多次失败后记录异常。

------

### 8.6 可恢复执行

系统启动后从数据库查询未完成任务继续执行。

任务状态不能只保存在进程内存中。

------

### 8.7 运行日志

每次LLM调用记录：

- Skill ID；
- Skill版本；
- 模型；
- Prompt版本；
- 输入数据摘要；
- 输出结果；
- Token消耗；
- 调用耗时；
- 错误信息；
- 重试次数。

------

## 9. 灵活性与扩展设计

MVP不建设平台，但保留三个核心扩展点。

### 9.1 新增分析原则

如果客户增加新的意向判断逻辑，优先通过：

- 修改Prompt；
- 增加Skill说明；
- 增加Few-shot；
- 发布新Skill版本；

完成。

不修改原始数据结构，也不侵入其他业务流程。

------

### 9.2 新增分析Skill

未来增加产品优缺点分析，可以增加：

```text
product_opinion_analysis
```

未来增加竞品分析，可以增加：

```text
competitor_comparison_analysis
```

未来增加舆情判断，可以增加：

```text
public_opinion_risk_analysis
```

这些Skill复用已有：

- 视频数据；
- 评论数据；
- 视频语境；
- 用户信息；
- Skill执行器；
- 分析结果表。

------

### 9.3 新增业务工作流

MVP阶段工作流可以直接使用代码配置。

线索获客工作流：

```text
video_context_analysis
→ comment_lead_screening
→ user_lead_analysis
```

未来产品分析工作流：

```text
video_context_analysis
→ product_opinion_analysis
→ product_opinion_summary
```

未来竞品分析工作流：

```text
video_context_analysis
→ competitor_comparison_analysis
→ competitor_insight_summary
```

首期不建设通用DAG平台，待实际出现多个复杂工作流后再升级。

------

### 9.4 实时分析扩展

MVP当前以批处理和异步分析为主。

为了未来支持舆情监控，当前只需要保证：

- 数据可以增量导入；
- 单条或小批评论可以触发分析；
- 工作流不依赖全量日批；
- 分析结果带时间信息；
- 评论与视频之间关系完整。

未来真正出现实时舆情需求时，再增加：

- 消息队列；
- 实时评论事件；
- 时间窗口统计；
- 风险告警；
- 深度LLM复核。

## 10. 评测体系

### 10.1 MVP核心评测指标

#### 评论筛选指标

- 无意义评论过滤准确率；
- 购车相关评论识别准确率；
- 高意向评论召回率；
- 疑似营销评论识别准确率；
- 无效评论误入率。

#### 用户分级指标

- H级准确率；
- H/A级合并准确率；
- H/A/B/C混淆矩阵；
- 高意向用户召回率；
- 分级稳定性；
- 证据引用准确率。

#### 画像指标

- 目标品牌车型准确率；
- 核心需求准确率；
- 主要顾虑准确率；
- 购车阶段准确率；
- 无证据推断率；
- 销售切入点可用率。

#### 工程指标

- JSON输出合格率；
- 任务成功率；
- 自动重试成功率；
- 平均单评论分析成本；
- 平均单用户分析成本；
- 分析耗时。

------

### 10.2 业务验证指标

业务侧重点关注：

- 每万条评论产出的有效线索数量；
- H/A级线索人工认可率；
- H级线索人工认可率；
- 销售人员认为可跟进的线索比例；
- 私信回复率；
- 有效沟通率；
- 联系方式获取率；
- 试驾预约率。

MVP阶段应重点验证前三项，不必立即以最终成交率评价系统。

------

### 10.3 测试集建设

建议在MVP阶段建立小规模人工标注集。

至少覆盖：

- 无意义评论；
- 正面但无购车意向评论；
- 普通产品兴趣；
- 浅层配置讨论；
- 竞品比较；
- 询价；
- 置换；
- 试驾；
- 购车时间；
- 负面情绪中包含换车需求；
- 疑似营销；
- 疑似水军；
- 玩梗；
- 信息不足。

人工标注集既用于Prompt调优，也用于后续模型切换和版本回归。

## 12. 主要风险与应对策略

### 12.1 正面情绪被误判为购车意向

**风险：**

“好看”“喜欢”“厉害”等评论可能被模型错误识别为高价值线索。

**应对：**

- 在评论Skill中明确区分情绪、兴趣、需求和行动；
- 增加典型负样本Few-shot；
- H/A等级必须存在具体需求或行动证据。

------

### 12.2 水军和真实用户难以区分

**风险：**

真实用户也可能使用夸张语言，单条评论很难准确判断。

**应对：**

- 输出“疑似营销”而不是绝对定性；
- 综合用户多条评论和主页信息；
- 允许人工修正；
- 后续根据真实案例增加独立风险Skill。

------

### 12.3 用户主页数据不足导致过度画像

**风险：**

根据头像、昵称和少量视频推断职业、收入或家庭情况，容易产生无依据结论。

**应对：**

画像严格限定为与购车转化相关的内容：

- 关注品牌车型；
- 购车阶段；
- 核心需求；
- 主要顾虑；
- 购车时间；
- 使用场景。

没有证据的信息保持未知。

------

### 12.4 H/A/B/C标准重叠

**风险：**

不同评论可能同时符合多个等级特征。

**应对：**

以购车决策阶段和行动信号为主要判断标准：

- H：交易或行动；
- A：主动评估；
- B：产品兴趣；
- C：弱相关表达。

通过标注集和Few-shot固化边界。

------

### 12.5 批量评论处理可能相互干扰

**风险：**

批量输入可能导致评论ID和结果错位，或一条评论影响另一条评论判断。

**应对：**

- 每条评论必须带唯一ID；
- 输出数量必须与输入数量一致；
- Schema校验评论ID；
- 超长评论单独处理；
- 对异常批次拆分重试。

------

### 12.6 LLM输出不稳定

**风险：**

出现JSON错误、字段缺失或不遵守分级规则。

**应对：**

- 使用低温度；
- 强制JSON Schema；
- 提供清晰Few-shot；
- 自动重试；
- 使用稳定的Skill版本；
- 建立回归测试集。

------

## 13. 当前架构的适用边界

该MVP架构适合：

- 快速验证线索筛选价值；
- 小到中等规模评论批量分析；
- 多模型Prompt调优；
- 新增少量分析Skill；
- 在一周左右完成首版开发。

当前不适合：

- 百万级评论秒级实时处理；
- 大规模复杂事件流；
- 多租户高度差异化规则；
- 数十个相互依赖的分析工作流；
- 完整销售CRM；
- 在线模型训练和自动学习。

当业务验证成功、数据规模和应用数量显著增长后，再逐步升级：

1. 引入专业任务队列；
2. 拆分高负载模块；
3. 增加工作流编排；
4. 引入实时事件处理；
5. 建设独立Prompt和Skill管理平台；
6. 建设更完整的业务应用层。

------

## 14. 结论

“线索获客”项目的MVP总体架构可以概括为：

> 五层逻辑架构、模块化单体应用、三个核心LLM Skill、一条固定分析工作流、统一分析结果存储和简单线索应用。

核心组成如下：

```text
L1 数据与证据层
视频、评论、用户主页、原始数据

L2 事实与特征层
视频语境、评论意向、用户聚合和简单统计

L3 AI分析能力层
视频语境理解、评论线索筛选、用户综合分析

L4 业务策略层
线索有效性、H/A/B/C分级、购车意向画像和销售建议

L5 业务应用层
线索列表、线索详情、人工审核和结果导出
```

该设计没有提前建设重量级平台，但保留了必要的扩展能力：

- 新判断原则通过Prompt和Skill版本扩展；
- 新分析任务通过新增Skill扩展；
- 新业务场景通过新增固定工作流扩展；
- 新模型通过LLM Gateway替换；
- 新版本可以基于历史数据重新运行；
- 未来实时需求可以在现有数据和Skill基础上逐步升级。

项目首期最重要的成功标准不是技术架构是否完整，而是：

> 能否在真实评论数据中稳定识别出业务人员认可的H/A级购车线索，并形成可解释、可验证、可跟进的销售结果。

只有这一核心价值被验证后，系统才有必要进一步平台化和规模化。

## 15. 快速开始（V0）

```bash
# 1. 安装依赖
python -m pip install -r requirements.txt

# 2. 配置环境（复制后填写 MySQL 与 LLM 配置）
copy .env.example .env

# 3. 启动服务（自动建表并启动后台 Worker）
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
```

打开 http://localhost:8000 ：导入 `data/test_data.xlsx` → 启动分析 →
在 `/leads` 查看、审核和导出线索。

清空当前业务数据：
python scripts/clear_data.py          # 显示各表行数，输入 yes 确认后清空
python scripts/clear_data.py --yes    # 跳过确认直接清空

## 16. V1 API 与部署

V1 将系统微服务化，对外提供 Bearer 认证的异步 HTTP API：

- `POST /api/v1/comment-screening`：提交评论筛选任务，返回 `job_id`；
- `POST /api/v1/profile-analysis`：提交用户主页综合分析任务（支持多模态识图），返回 `job_id`；
- `GET /api/v1/jobs/{job_id}`：轮询任务状态与结果。

所有接口需在请求头携带 `Authorization: Bearer <API_KEY>`（`API_KEYS` 在 `.env` 中配置）。

部署步骤：

```bash
# 1. 配置环境（复制后填写 API_KEYS、MySQL 与 LLM 配置）
copy .env.example .env

# 2. 构建并启动全部服务
docker compose up -d --build
```

完整设计见 `claude_docs/2026-07-23-v1-design.md`。
