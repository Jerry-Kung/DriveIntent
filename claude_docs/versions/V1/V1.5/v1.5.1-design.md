# V1.5.1 设计：定级终判调整——"已购"信号封顶 + 多条相近评论合并增强

> 版本：V1.5.1 | 日期：2026-08-06

## 1. 背景与目标

V1.5 大版本的主题是对初筛（Agent1）和定级（Agent2）两个 Agent 的工作流程做细节优化，解决测试中发现的初筛/定级结果不准确问题。V1.5.1 是该系列第一个补丁，解决两个定级问题：

1. **"已购"类评论定级过高**：当前工作流把"已购""已大定""已提车""已下单"等**已完成购买动作**的评论统一视作购买行为/购买倾向，给出很高的定级。但近期已购车的客户基本不可能短时间内继续购车，对销售动作没有价值。此类评论可以通过初筛，但定级结果原则上不应高于 B 级。
2. **多条相近评论未被合并增强**：同一用户短期内发布多条内容和倾向接近、对购车倾向有积极印证作用的评论（如在多个汽车视频下持续讨论购车、对某款车反复表达兴趣），表明其购车兴趣/意愿大概率强于一般用户，且社交媒体活跃用户更利于销售沟通，应可酌情上调一级。当前定级不体现这一点。

**约束**：本版本仅通过修改 Prompt 实现，不调整工作流（不增加新的升降级判断节点）。工作流重构待后续统一组织。

## 2. 关键概念澄清

- **"已购" ≠ "车主"**：`is_car_owner` 标签要求"大概率已购车"的综合判定；而单独一条"已下单"评论可能不足以判定车主，但属于本版本要处理的"已购"信号。封顶规则以**评论内容中的已购信号**为准，与车主标签判定相互独立、互不影响。
- **合并增强只看"购车倾向"相关评论**：内容相似但与购车倾向无关的评论（反复玩梗、重复夸赞外观）不构成上调依据。
- **裁量权下放**：两条规则均为原则性规则，具体是否触发由 LLM 结合证据酌情裁量，不设硬性量化门槛（不规定"几条算多""多久算短期"）。

## 3. 方案：评级流水线新增"第四段：终判调整"

`user_lead_analysis` Prompt 的评级流程由三段改为四段流水线：

```
基线评级 →(match_adjustment)→ 中间1 →(profile_adjustment)→ 中间2
        →(第四段：merge_boost / purchase_downgrade)→ lead_grade
```

第四段内部按固定顺序执行两条规则（先合并增强、后已购封顶）：

### 规则 1：多条相近评论的合并增强（酌情上调）

- 用户发布过多条内容相近、且对购车倾向有积极印证作用的评论 → 可酌情上调一级（B→A、A→H）。
- 仅"购车倾向"相关的相近评论参与判断；是否上调由 LLM 结合评论数量、时间跨度、内容质量综合裁量。
- 边界：等级为 C 不参与上调；上调上限为 H。
- 审计输出：触发时 `merge_boost="upgraded"`、`merge_boost_reason` 写明依据；未触发 `"none"` / null。

### 规则 2："已购"信号封顶（原则性降级）

- 评论内容包含**已完成购买动作**的信号（包括但不限于"已下单""已大定""已提车""已购"）→ 无论前三段结果如何、无论是否判定为车主，最终等级**原则上不高于 B 级**（高于 B 压到 B；原为 C 保持 C）。
- **豁免**：用户同时有明确的新增购车意向证据（如"刚提车，想再买一台给家里人""已提车但空间太小打算换了"）→ 可不受封顶限制，由 LLM 酌情判断；豁免时必须写明具体的新增意向证据。
- **时效性引导**：判断已购信号时可参考评论 `comment_time`——距今较久（如一年以上）的已购评论，"短期内不会再购车"的推定减弱，可结合其他证据酌情放宽封顶，同样由 LLM 裁量。
- 审计输出：触发封顶 `purchase_downgrade="capped"`、`purchase_downgrade_reason` 写明识别到的已购信号；有豁免证据未封顶时为 `"none"` 且 reason 写豁免依据；无已购信号时 `"none"` / null。

### 优先级

规则 2 优先级高于规则 1：两者同时触发时先上调后封顶（执行顺序天然保证），最终仍不高于 B。

## 4. 改动清单

### 4.1 Prompt（核心改动）

新建 `app/skills/prompts/user_lead_analysis_v1.5.1.txt`，基于现行 v5 修改：

1. 评级流程声明"三段"改"四段"，第三段后追加【第四段:终判调整】（内容见第 3 节）；
2. 输出 JSON 模板增加 4 个字段：`merge_boost` / `merge_boost_reason` / `purchase_downgrade` / `purchase_downgrade_reason`；
3. `analysis_text` 分段说明由五段改为六段（增加"终判调整"段）；
4. 其余段落（独立标签、意向主体判断、第一至三段、输出要求）不动。

旧文件 `user_lead_analysis_v5.txt` 保留不动、不再被引用（VERSIONING.md 规则）。

### 4.2 代码配套

| 文件 | 改动 |
|---|---|
| `app/schemas/skills.py` | `UserLeadResult` 加 4 个带默认值的内部审计字段（见下），不进对外 API 契约 |
| `app/skills/configs/user_lead_analysis.yaml` | `version: "1.5.1"`、`prompt_file: user_lead_analysis_v1.5.1.txt`、`prompt_version: "v1.5.1"`；description 同步"三段"→"四段"表述 |
| `app/workflow/pipeline.py` | `SKILL_VERSIONS[USER_ANALYSIS_SKILL]` → `"1.5.1"` |

Schema 新增字段：

```python
# V1.5.1：终判调整审计字段（内部用，不进对外 API 契约）。
# 审计链条：baseline →(match)→ 中间1 →(profile)→ 中间2
#          →(merge_boost / purchase_downgrade)→ lead_grade
merge_boost: str = "none"            # none | upgraded
merge_boost_reason: str | None = None
purchase_downgrade: str = "none"     # none | capped
purchase_downgrade_reason: str | None = None
```

默认值保证旧结果反序列化与不含新字段的 LLM 输出均兼容。

### 4.3 明确不改动

- `comment_lead_screening` 及其他 Skill（"已购"类评论本就应通过初筛，符合预期）；
- 工作流结构（无新任务节点，两条规则均在 `user_lead_analysis` 单次 LLM 调用内完成）；
- 对外 API 契约（新字段仅内部审计）；
- `GRADING_STANDARD` 常量（H/A/B/C 等级定义未变）。

### 4.4 影响说明

`SKILL_VERSIONS` 升版使 V0 流水线路径上旧版本 `user_lead_analysis` 分析结果失效并触发重分析（与历史升版行为一致）；API 路径无状态，不受影响。
