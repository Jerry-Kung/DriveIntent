# V1.9.2 设计：疑似黑名单账号识别

> 版本：V1.9.2 | 日期：2026-09-08

## 1. 背景与目标

V1.9.0 建立了"人工黑名单"机制：`account_douyin_id` 命中 `blacklisted_user` 表的
账号在精筛定级前被零 LLM 短路，直接输出"黑名单用户"。V1.9.1 为其补了对外增删查 API。

但黑名单的**发现**仍依赖人工外部判断：系统自身不识别异常账号。本版本在"用户精筛
定级"（Agent2）工作流中新增对 **疑似黑名单账号** 的自动识别，把判断结果通过
API 接口返回，供前端在拉黑异常账号时参考：

1. 识别点在既有 `user_lead_filter`（无效用户过滤）节点——该节点本就用于识别异常
   用户，且已获得"全部评论 + 主页画像"完整证据包，复用工作量最低；
2. 识别两类疑似黑名单账号：**疑似营销号**、**疑似虚假账号**；
3. 一旦认定疑似黑名单，**直接返回、不进后续定级流程**（与现有过滤命中同款行为）；
4. 结果以三个字段对外透出，供前端参考。

## 2. 范围决策（已与需求方确认）

| 决策点 | 结论 |
|---|---|
| 识别位置 | `user_lead_filter` 的 LLM 判定内，**零新增 LLM 调用**（复用该节点唯一一次调用）。 |
| 命中后行为 | 命中疑似黑名单 → 直接合成 C 级结果（`is_valid_lead=False`），跳过定级/复核/润色；且优先于既有的六类无效用户过滤类别。 |
| 接入范围 | **API 与 V0 两路径都生效**（两路径共用 `run_user_filter`）。注意：与 V1.9.0 的"确认黑名单"不同——后者为数据库精确匹配仅 API 路径接入；V1.9.2 是 LLM 判定，跟随过滤节点天然覆盖两路径。 |
| 对外契约 | **纯增量**：新增 `is_blacklisted` / `blacklist_type` / `blacklist_reason` 三字段。既有字段（含 `has_value=false` + analysis 文本）行为不变。 |
| 字段命名 | bool 用 `is_blacklisted`；type 用**中文枚举** `"confirmed"` / `"营销号"` / `"虚假账号"`；reason 为中文说明。三字段对非黑名单账号为空/空串（`false` / `null` / `null`）。 |
| 确认黑名单口径 | V1.9.0 的数据库命中也统一进三字段（type=`"confirmed"`），不新增 LLM 调用。 |
| 数据来源 | 仅**用户主页截图识别的画像**（`homepage_profile`，含 `fans_count`/`likes_count`/`follow_count`/`verification`/`signature`/`content_themes`/`raw_description`）与**评论内容**。作品数识图未结构化产出，由 `raw_description`/`content_themes` 推断；无相关内容时**跳过对应判断**，不设额外数据源/API。 |

## 3. 识别规则（prompt 内，LLM 判定）

### 3.1 疑似营销号（满足以下其中一条即认定）

| # | 规则 | 命中信号 |
|---|---|---|
| M1 | 昵称/简介出现职业身份 | 销售、顾问、汽车贸易、车行、二手车、经销商、媒体、代运营等 |
| M2 | 昵称/简介出现商业联系方式/获客 CTA | 微信、电话、同号、私聊、报价、主页联系等 |
| M3 | 内容长期大量涉及商业营销 | 报价、库存、交付、促销等，或跨品牌的行情、金融、政策等内容 |
| M4 | 评论区截流 | "找我"、"我这里便宜"、"有现车"、"全国发"等引流话术 |
| M5 | 企业/机构认证 | 汽车相关蓝 V / 机构认证身份 |

### 3.2 疑似虚假账号（满足以下其中一条即认定）

| # | 规则 | 命中信号 | 说明 |
|---|---|---|---|
| F1 | 零作品 + 高粉丝 | 作品=0 且粉丝>1 万 | 截图可见 |
| F2 | 极少作品 + 大量粉丝 | 作品<5 且粉丝>5 万 | 截图可见 |
| F3 | 高粉低互动 | 粉丝>1 万 且 累计获赞/粉丝 < 0.1 | 截图可见 |
| F4 | 模板内容/评论 | 作品/评论大量高度相似内容 | 避免误判：**高度相似评论需数量>50** |

> 阈值（1 万 / 5 万 / 0.1 / 50 条）为设计基准值，写入 Prompt 供 LLM 遵循；
> 无对应截图信息时跳过该规则（见 §2 数据来源）。

### 3.3 判定原则

- 综合**全部评论 + 主页画像**整体判断，严禁凭单条评论片面定性；
- **宁放过勿误杀**：证据不足、情形模糊、多种解释并存时一律判非黑名单（放行后续
  定级流程）——这与既有 `user_lead_filter` 的 fail-open 基调一致；
- 与既有六类"无效用户过滤"类别并行：若同时符合"疑似营销号"与既有的
  `marketing_suspect` 过滤类别，**疑似黑名单优先**（更利于前端拉黑）。

## 4. 对外契约（纯增量）

`ProfileResult`（`app/api/schemas.py`）新增三字段：

| 字段 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `is_blacklisted` | `bool` | `false` | 是否被判定为黑名单用户（含确认/疑似） |
| `blacklist_type` | `str | None` | `null` | 黑名单类型：`"confirmed"` / `"营销号"` / `"虚假账号"`；非黑名单为 `null` |
| `blacklist_reason` | `str | None` | `null` | 判断理由（中文）；非黑名单为 `null` |

内部三个 Schema 同步新字段，语义一致：

- `UserFilterResult`：`is_blacklisted`(bool, false)、`blacklist_type`(Literal
  `"营销号"`/`"虚假账号"`，null)、`blacklist_reason`(str, null)。仅 LLM 过滤节点判定
  "疑似"两类；`"confirmed"` 不在过滤节点输出，由确认黑名单短路直接给定。
- `UserLeadResult`：`is_blacklisted`(bool, false)、`blacklist_type`(str, null)、
  `blacklist_reason`(str, null)。
- `ProfileResult`（对外）：同第二行，`blacklist_type` 为 `str`。

### 4.1 各场景对外表现

| 场景 | `is_blacklisted` | `blacklist_type` | `blacklist_reason` |
|---|---|---|---|
| 确认黑名单（V1.9.0 命中表） | `true` | `"confirmed"` | `"该抖音号已列入系统黑名单"` |
| 疑似营销号（V1.9.2 LLM 判定） | `true` | `"营销号"` | 中文理由 |
| 疑似虚假账号（V1.9.2 LLM 判定） | `true` | `"虚假账号"` | 中文理由 |
| 非黑名单 | `false` | `null` | `null` |
| 该条处理失败（异常兜底） | `false` | `null` | `null` |

## 5. 实现

### 5.1 代码改动

| 文件 | 改动 |
|---|---|
| `app/schemas/skills.py` | `UserFilterResult` / `UserLeadResult` 各加三字段 |
| `app/api/schemas.py` | `ProfileResult` 加三字段 |
| `app/skills/user_filter.py` | `run_user_filter` 增加"输出非法即 fail-open"：`is_blacklisted=true` 但缺 `blacklist_type` → 按非黑名单放行；`build_filtered_lead_result` 透传三字段 |
| `app/api/agent2.py` | 确认黑名单短路补三字段（`type="confirmed"`）；过滤命中分支前增加疑似黑名单短路径（`is_blacklisted=true` → 直接合成 C 级，跳过定级/复核/润色）；异常兜底补三字段（`false`/`null`/`null`） |
| `app/api/mapping.py` | `map_profile_result` 两个分支均透传三字段 |
| `app/workflow/pipeline.py` | `run_user_analysis`（V0 路径）复用 `build_filtered_lead_result` 透传；无需改 `SKILL_VERSIONS` |

### 5.2 `agent2.py` 分支顺序（每账号）

```text
1. 确认黑名单（blacklist 命中）→ 合成 C，type="confirmed"，跳过所有 LLM
2. has_comments 为空 → 合成 C（is_blacklisted=false）
3. 识图 → run_user_filter（一次 LLM）
   a. is_blacklisted=true → 合成 C，type="营销号"/"虚假账号"，跳过定级/复核/润色
   b. 六类过滤命中（filtered=true）→ build_filtered_lead_result
   c. 否则 → analyze_account → 复核 → 润色
```

## 6. 明确不做（YAGNI）

- 不把疑似的判定结果**自动写入** `blacklisted_user` 表（只返回参考，由前端/人工决策）。
- 不做独立的"疑似黑名单" LLM 节点（复用过滤节点，零新增调用）。
- 不为识图增加"作品数"结构化字段（按需从 `raw_description` 推断，缺失即跳过）。
- 不改 `SKILL_VERSIONS`（`user_lead_filter` 无对应条目）。
- 不修改对外既有字段语义。

## 7. 测试要点

1. **Schema**：三字段默认值与类型校验（`UserFilterResult`/`UserLeadResult`/`ProfileResult`）。
2. **`run_user_filter`**：`is_blacklisted=true` 且缺 type → fail-open 放行；正常疑似命中透传。
3. **`build_filtered_lead_result`**：透传 `is_blacklisted`/`blacklist_type`/`blacklist_reason`。
4. **`map_profile_result`**：两分支（has_value 真/假）均透传三字段；非黑名单保持 false/null/null。
5. **`agent2` 集成**：
   - 疑似营销号：一次过滤调用后直接返回 C，`is_blacklisted=true`、`type="营销号"`，
     **定级/复核/润色未被调用**，`has_value=false`；
   - 疑似虚假账号：同款，`type="虚假账号"`；
   - 确认黑名单：type=`"confirmed"`，仍零 LLM 调用；
   - 未命中：正常走完整流水线，三字段 false/null/null；
   - 异常兜底：三字段 false/null/null。
6. **Prompt 渲染**：新规则关键词与三字段出现在模板；`is_blacklisted` 为 true 时
   `blacklist_type` 必须非空（Prompt 约束）。
7. **回归**：全量 `python -m pytest -q` 保持全绿（当前 401 passed，需同步改
   `test_user_filter.py` 的 v1.6.1 版本断言）。
