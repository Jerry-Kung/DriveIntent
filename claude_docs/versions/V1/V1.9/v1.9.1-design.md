# V1.9.1 设计：用户黑名单对外增删查 API

> 版本：V1.9.1 | 日期：2026-09-08

## 1. 背景与目标

V1.9.0 建立了用户黑名单机制：Agent2 精筛定级前对 `account_douyin_id` 做零 LLM
黑名单匹配，命中即短路输出"黑名单用户"。但黑名单的维护目前**只有内部管理面**：
`/blacklist` 页面与 `POST /api/blacklist`（表单） / `DELETE /api/blacklist/{id}`，
均为内网、无鉴权、表单编码，不能供外部前端直接对接。

本版本为黑名单提供一套**对外增删查 API**（与既有 Agent API 同层），供外部前端
驱动黑名单的录入、查询与删除。

## 2. 范围决策（已与需求方确认）

| 决策点 | 结论 |
|---|---|
| 鉴权 | **复用 API Key**：`Authorization: Bearer <API_KEY>`，与 `/api/v1/*` 既有接口一致；未配置 key 时放行（本地/测试默认，既有行为）。 |
| 路径/模块 | **新建 `app/api/blacklist.py`**，挂 `/api/v1/blacklist`；`main.py` 注册到 `app`。内部管理面 `/api/blacklist`、`/blacklist` 保留不动。 |
| 列表能力 | **分页 + 可选关键字/备注搜索**：`GET /api/v1/blacklist?page=&page_size=&q=`。`q` 从 `douyin_id` / `nickname` / `remark` 做子串匹配（`LIKE`）。 |
| 新增形态 | **JSON 数组批量 + 幂等统计**：`POST /api/v1/blacklist`，请求体 `{douyin_ids: [...], nickname?, remark?}`，返回 `{added, skipped, invalid}`。复用服务层 `add_blacklist`。 |
| 删除 | `DELETE /api/v1/blacklist/{blacklist_id}`，命中 `204`，未命中 `404`（与内部管理面同语义）。 |
| 命名 | 对外暴露 `blacklist_id`（表 `id`）作为删除定位标识；`douyin_id` 仍是业务匹配主体与查询键。删除一律用 `blacklist_id`（列表返回），不用 douyin_id 作为删除键，避免"重复 id / 不存在 id"歧义。 |
| V0 | 与 V1.9.0 相同：仅 API 路径，V0 不接入、不覆盖。 |

**对外契约**：本版本**纯增量**——新增一组 `/api/v1/blacklist` 接口，`/api/v1/jobs/*`
与分析结果结构零改动。既有内部管理面 `/api/blacklist`（表单、无鉴权）语义不变。

## 3. 对外接口契约

统一约定（沿用对接文档 §3）：JSON、UTF-8、时间戳 ISO 8601 东八区、`Authorization: Bearer`。

### 3.1 `GET /api/v1/blacklist`（查：分页列表）

请求 query 参数：

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `page` | int | 1 | 页码，从 1 起；<1 按 1 处理 |
| `page_size` | int | 20 | 每页条数；上限 100（超限截断为 100） |
| `q` | string | 空 | 可选；对 `douyin_id` / `nickname` / `remark` 做子串匹配（不区分大小写） |

响应 `200`：

```json
{
  "items": [
    { "blacklist_id": 1, "douyin_id": "79373130119",
      "nickname": "张三", "remark": "广告号",
      "created_at": "2026-09-08T10:00:00+08:00" }
  ],
  "total": 1, "page": 1, "page_size": 20
}
```

- `items` 按 `created_at` 倒序（新在前），`total` 为满足条件的总条数（不是本页条数）。
- `nickname` / `remark` 可空（`null`）；`created_at` 恒为东八区 ISO 8601。

### 3.2 `POST /api/v1/blacklist`（增：批量入库）

请求体：

```json
{ "douyin_ids": ["79373130119", "79373130120"],
  "nickname": "批量昵称", "remark": "批量备注" }
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `douyin_ids` | `array<string>` | 是 | 至少 1 条；每项须为纯数字字符串（合法抖音号） |
| `nickname` | string | 否 | 应用到本批入库的每条记录 |
| `remark` | string | 否 | 同上 |

响应 `200`：

```json
{ "added": 2, "skipped": 0, "invalid": 0 }
```

- `added` 新增入库条数；`skipped` 库内已存在（幂等跳过）；`invalid` 非法（非纯数字/空串）未入库。
- **非空校验**：`douyin_ids` 为空数组 → `422`。
- 请求体含非法项**不整体拒绝**：合法项照常入库，`invalid` 计数返回，由调用方决策（与 V1.9.0 语义一致）。
- 同批重复出现的合法 ID 只首次入库、其余计 `skipped`（服务层幂等，不变）。

### 3.3 `DELETE /api/v1/blacklist/{blacklist_id}`（删）

- 命中 → `204`（无 body）。
- 未命中 → `404` `{"detail": "黑名单记录不存在"}`。
- `blacklist_id` 为响应中的 `blacklist_id`（表 `id`）。

### 3.4 错误码

沿用对接文档 §3：`401`（鉴权）、`404`（删除未命中）、`422`（参数不合法，含空
`douyin_ids`、page 非法类型、Pydantic 校验失败）、`500`（服务内部错误）。

## 4. 数据访问层扩展（`app/services/blacklist.py`）

| 函数 | 职责 | 说明 |
|---|---|---|
| `list_blacklist(session, *, search: str \| None = None, offset: int \| None = None, limit: int \| None = None)` | 分页/搜索列表 | **向后兼容**：三参数缺省为 `None`，行为与现状完全一致（全量倒序），内部管理页与既有测试不受影响。`search` 非空时对 `douyin_id`/`nickname`/`remark` 做 `LIKE %q%`。 |
| `count_blacklist(session, *, search: str \| None = None) -> int` | 满足条件的总条数 | 供分页 total。 |

- `list_blacklist` 先 `count` 再查页；缺省参数路径不触发 count（保持内部页零行为变化）。
- 复用既有 `created_at desc, id desc` 排序。

## 5. API 层（`app/api/blacklist.py` 新建）

- 从 `app.api.routes` import `get_db`、`require_api_key`（复用，不复制）。
- `blacklist_api_router = APIRouter()`，三条路由均 `dependencies=[Depends(require_api_key)]`。
- `created_at` 经与 `routes.py` 相同的 `_TZ8` 转东八区 ISO 8601。
- Pydantic 请求模型：`BlacklistAddRequest(douyin_ids: list[str], nickname: str | None = None, remark: str | None = None)`；`douyin_ids` 空数组在 handler 层判 `422`。
- 响应用 `dict`（沿用管理页 style）或轻量 Pydantic 模型（`blacklist_id`/`douyin_id`/`nickname`/`remark`/`created_at`）；不新增对外契约字段到既有接口。
- `q` 搜索、`page`/`page_size` 归一化（<1→1，>100→100）在 handler 层完成。

## 6. 文档与版本化资产

- **无 Prompt / Skill 变更**（纯代码层 API，零 LLM）：不新增/修改 Prompt 文件、
  不升 `prompt_version` / Skill `version`、不改 `SKILL_VERSIONS`。
- `docs/DriveIntent-V1-API对接文档.md`：新增"黑名单管理 API"章节（§，端点/参数/响应/错误码），
  对接文档版本号 `1.3 → 1.4`，更新页首版本与日期。
- `claude_docs/versions/V1/OVERVIEW.md`：能力快照补对外黑名单 API 条目 + 变更索引加 V1.9.1 行。
- `docs/DriveIntent-部署文档.md`：若 §7 有接口清单则补 `/api/v1/blacklist`（如相关；主文新增说明）。

## 7. 明确不做（YAGNI）

- 不做黑名单批量导出 / 文件导入（对外仍为 JSON，内部管理页现状不改）。
- 不做单条 get-by-id（`GET /api/v1/blacklist/{id}`）——外部查询经分页列表已覆盖。
- 不做更新（update）接口（改 nickname/remark 目前无需求；V1.9.0 亦无）。
- 不接入 V0（同 V1.9.0）。
- 不给内部管理面 `/api/blacklist` 加鉴权（内网管理面，与 `/audit` 同层）。

## 9. 风险与边界

- 路由冲突：内部 `blacklist_router` 已注册 `POST /api/blacklist` 与
  `DELETE /api/blacklist/{id}`；新路由为 `/api/v1/blacklist` 前缀，与内部面
  `/api/blacklist` **路径不同、不冲突**。`GET /api/v1/blacklist` 亦不与既有
  `/api/v1/*` 冲突。
- 部署侧无需建表/迁移：V1.9.0 已由 `create_all` 建 `blacklisted_user` 表，本版本仅加读接口。
