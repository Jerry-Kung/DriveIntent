## 1. 目标与范围

把 `config/our_models.json` 中的**在售车型信息全方位纳入 Agent2（账号画像精筛）评级**，修复评级失真问题：

- **问题**：当前 `user_lead_analysis_v3` 虽已注入 `our_models_summary`，但仅在提示词末尾有一条叙述性弱规则（"价位/品类差异显著时适当下调"）——无分档标准、无上调路径、无审计字段、分析文本不强制体现比较。导致用户对与我方车型（东风猛士 M817/917）完全无关的车型（如五菱宏光）表现出强购车意向时，仍被判为高意向线索。
- **目标**：把这条弱规则升级为与 V1.2 画像上调同等地位的**结构化匹配度调整机制**：意向指向我方车型可上调、同类/竞品不调、部分相关降一级、完全无关降两级；分析过程与评级理由全方位体现意向车型与在售车型的比较。

**对外 API 契约不变**——对接方无需改动解析逻辑。

### 1.1 不做

- 不改 Agent1（评论初筛）链路及其已有的 `app/matching/downgrade.py` 视频语境降级逻辑。
- 不改对外输出字段结构（`intent_level` / `value_score` / `profile_tags` 等不变）。
- 不引入全市场车型库做代码层相似度匹配（意向车型的价位/品类由 LLM 常识现场判断）。
- 不改 `our_models_summary` 的构建与注入逻辑（两条调用链均已注入）。

## 2. 四档匹配度判定标准

LLM 依据 `our_models_summary` 中我方车型的价位/品类/用途信息，结合对用户意向车型的常识（如五菱宏光约 4-6 万微面/微客），现场判定匹配档位 `model_match_level`。四档之外另设 `unknown` 兜底态（无法判档，不属于匹配度档位）：

| 档位 | 判定标准 | 调整幅度 |
|------|---------|---------|
| `our_model` | 意向直指我方品牌/在售车型（东风猛士、M817/917 及别名） | 可上调一级（LLM 裁量：须有明确购车意向证据，单纯提及可不调） |
| `similar` | 同类/竞品：品类与价位均与我方某款车型接近（如坦克500、方程豹豹8） | 不调 |
| `partial` | 部分相关：品类或价位仅一项接近 | 降一级 |
| `unrelated` | 完全无关：品类与价位均差距显著（如五菱宏光） | 降两级 |
| `unknown` | 评论中识别不出具体意向品牌/车型，或我方车型未配置 | 不调 |

- 多款意向车型时，取与我方**最匹配**的一款判档（就高不就低）。
- 我方车型信息为"未配置"占位文本时，一律 `unknown`、零调整（与现状行为一致）。

## 3. 三段流水线评级

在 V1.2 已有"基线评级 → 画像上调"两段之间**插入匹配度调整段**：

1. **基线**：仅凭评论证据定 `baseline_grade`（H/A/B/C），画像与匹配度均不参与，与 V1.2 一致。
2. **匹配度调整**：按第 2 节档位对基线升/降级，得到中间等级。边界规则：
   - 基线 **C 不参与调整**（C 已是最低档；弱意向不因提及我方车型而升级）；
   - 降级下限为 C（如基线 B 遇 `unrelated`，降到 C 为止）；
   - 上调上限为 H（基线 H 不再上调）。
3. **画像上调**：V1.2 规则原样作用于第 2 段的结果——中间等级为 B 或 A 且 `homepage_profile` 有直接证据 → 再上调一级，最多一级。

两类上调理论上可叠加（B →匹配上调→ A →画像上调→ H），但每环节各自最多一级、各自要求直接证据。降级与画像上调可同时发生（H →降两级→ B →画像上调→ A）。

**分析内容要求**（写入 prompt）：

- `analysis_text` 从四段扩为**五段**：评论行为 / 购车阶段 / **意向车型与在售车型匹配度** / 主页画像 / 综合评分，需说明基线、匹配档位与各段调整。
- `lead_summary` 与 `recommended_entry_point` 要求体现与我方车型的关联（如"关注竞品坦克500，可从空气悬架差异切入"）。

## 4. 内部审计字段

`UserLeadResult` schema 新增三个字段（可选、有默认值），写入 `AnalysisResult` 便于调试与审计，**不改对外契约**：

| 字段 | 类型 | 说明 |
|------|------|------|
| `model_match_level` | `Literal["our_model","similar","partial","unrelated","unknown"]` | 匹配档位，默认 `unknown` |
| `match_adjustment` | `int` | 匹配度调整幅度，-2～+1，默认 0（负为降级、正为上调） |
| `match_reason` | `str \| None` | 判档与调整依据（意向车型与我方车型的价位/品类比较），不调可为 null |

中间等级不单独存字段，可由 `baseline_grade + match_adjustment` 推导。完整审计链条：

```
baseline_grade →(match_adjustment)→ 中间等级 →(profile_adjustment)→ lead_grade
```

## 5. 数据流与契约

```
build_our_models_summary(load_our_models())  ← 复用现状，两条链路均已注入
                    ↓
user_lead_analysis (v4)：基线 → 匹配度调整（四档） → 画像上调
                    ↓
输出 lead_grade(最终) + baseline_grade / model_match_level / match_adjustment
     / match_reason / profile_adjustment / adjustment_reason
                    ↓
map_profile_result() → 对外 intent_level/value_score/...（契约不变）
```

- 8100 对外 API 链路（`app/api/agent2.py::run_profile_analysis`）与 8000 流水线链路（`app/workflow/pipeline.py::run_user_analysis`）共用 `user_lead_analysis` skill，同时生效，无需改注入代码。
- `map_profile_result()` 映射逻辑不变，新增审计字段不进入对外输出。

## 6. 测试

沿用 V1.2 测试模式（mock LLM）：

- **Prompt 渲染**：v4 模板含四档规则关键内容，`$user_evidence_json` / `$grading_standard` / `$our_models_summary` 占位符齐全。
- **契约测试**：`UserLeadResult` 新字段默认值正确（LLM 未输出新字段时向后兼容不报错）、`model_match_level` 取值校验。
- **端到端（fake LLM）**：构造"意向五菱宏光、基线 H、`unrelated` 降两级至 B"的输出，断言审计字段落库、对外 `intent_level` 按降级后等级映射。
- **对外契约不泄漏**：`ProfileResult` 序列化结果不含 `model_match_level` / `match_adjustment` / `match_reason`。
- **未配置回归**：`our_models.json` 缺失时 summary 为占位文本，评级行为与现状一致（`unknown`、零调整）。
