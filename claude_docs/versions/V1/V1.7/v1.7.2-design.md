# V1.7.2 设计：评论初筛 ID 抄写移出 LLM——index 临时序号方案

> 版本：V1.7.2 | 日期：2026-08-24

## 1. 背景与问题

2026-08-23「评论初筛」6794 条任务中有 3246 条报执行失败，后端日志无错误、
LLM 日志（数万次调用）仅十几次失败。排查定位：失败作业全部是**单条评论作业**
（`progress_total=1`），且全部对应同一条评论（`comment_id=7675544453021549371`，
content=`[赞]`），`attempt_count=3`、`error="全部条目处理失败"`。

根因在**对外 API 路径**（8100）的 `app/api/agent1.py:run_comment_screening`：

- LLM 被要求"原样回传 comment_id"（19 位纯数字）；
- 当前主力 LLM 是廉价模型（成本优先），抄写长数字 ID 出错率天然偏高；
- 同一天 15340 次初筛 LLM 调用全部成功、0 失败——说明**不是 LLM 挂了，而是 ID
  抄错了**；抽样 20/20 条失败作业均为 comment_id 转录错误（插入"530"或丢末位）；
- API 路径对"ID 对不上"的处理是**静默兜底**（`agent1.py` 第 84 行：匹配不到就
  标 `passed=false, error="筛选失败"`），不抛异常、不记日志；三次重试都在重复
  抄同一个易错 ID，抄错后静默判失败。

对比 8000 测试流水线（`pipeline.py`）本就有 ID 集合校验 + 拆半重试，所以只在
API 路径暴雷。

## 2. 方案决策：index 临时序号，ID 操作移出 LLM

**拒绝重试式修复**：廉价模型抄 ID 的出错概率不会因重试而消失，重试只是把同一枚
硬币再抛几次。

改为**把 ID 从"需要 LLM 复述的数据"降级为"无需 LLM 接触"**：

1. **输入侧**：按批次内顺序给每条评论编临时 `index`（0..n-1），真实 `comment_id`
   不进任何喂给 LLM 的字段；
2. **输出侧**：LLM 回传 `index`（小整数），而非 `comment_id`；
3. **代码侧（LLM 之外）**：按 `index` 在批次内查表还原真实 `comment_id`，并做
   **集合校验**——返回的 index 集合必须恰好等于 `{0..n-1}`，任何缺失/重复/越界
   都抛 `ValueError` 交由 SkillExecutor 重试，而非静默张冠李戴。

LLM 要抄的对象从 19 位长数字变成 0/1/2 这类极短 token，抄错率下降数个数量级；
即便抄错也逃不过确定性代码校验，变为显式失败（重试/拆半），不再静默降级。

> 相比"纯位置对齐"（不输出 index），显式 index 更稳：纯位置对齐在 LLM 漏掉/
> 多出一条时会整体错位静默张冠李戴，而 index + 集合校验能精确发现遗漏与重复。

## 3. 改动清单

### 3.1 Schema（`app/schemas/skills.py`）

- 抽出 `_ScreeningFields`（无标识键的判定字段），`CommentScreeningItem` 继承之
  并加 `comment_id`（落库/下游契约，字段序列与历史落库完全一致，无兼容风险）。
- 新增 LLM 面向模型 `CommentScreeningBatchItem`（`index: int` + 判定字段）与
  `CommentScreeningBatchResult`（`items`）。

### 3.2 Prompt（v3 → v1.7.2，删除 `comment_lead_screening_v3.txt`）

- 输入示例 `{"comment_id": …}` → `{"index": 0, "content": …}`；
- 输出示例 `comment_id` → `index`；要求改为"index 集合须与输入完全一致，不得
  遗漏、重复或新增"；明示"无需接触任何真实评论 ID"。

### 3.3 代码层映射（新模块 `app/skills/screening_batch.py`）

- `build_screening_input(video_context, comment_pairs)`：编 index，构造上下文；
- `map_batch_result(batch, comment_ids)`：校验 index 集合 == `{0..n-1}`，还原为
  `CommentScreeningResult`（真实 comment_id）。

两路径共用该模块，保证输入/输出契约一致。

### 3.4 两条路径接入

- **8000**（`pipeline.py`）：`_call_screening` 改用 index 输入/输出 + 映射；
  `screen_comment_batch` 的重试循环捕获映射层 `ValueError` 重试，拆半递归保留
  （单条仍失败抛 `SkillExecutionError`）。
- **8100**（`agent1.py`）：`_screen_batch` 同改；`run_comment_screening` 的批次
  try/except 与兜底逻辑不变（映射层抛错时整批进 `errors`，作业层面 `fail_or_retry`）。

### 3.5 版本号（遵循 VERSIONING.md 第 4 节）

- `SKILL_VERSIONS[COMMENT_SCREENING_SKILL]`：`"1.3"` → `"1.7.2"`
- `app/skills/configs/comment_lead_screening.yaml`：`version="1.7.2"`、
  `prompt_file=comment_lead_screening_v1.7.2.txt`、`prompt_version="v1.7.2"`

## 4. 契约影响

- **对外 API 契约不变**：`/api/v1/comment-screening` 的请求/响应字段（`comment_id`、
  `passed`、`filter_type`、`is_car_owner`、`has_purchase_intent` 等）不变。变化的
  只是后端与 LLM 之间的**内部**输入/输出格式。
- **落库契约不变**：`AnalysisResult.result`（8000）与 `api_job.result`（8100）的
  `comment_id` 键保留，`mapping.py` / `aggregation.py` 下游零改动。
- **版本升档副作用**：`get_current_result` 按 `skill_version` 取结果，升到 1.7.2
  后 8000 链路会按新版本重建评论筛选任务（`create_task` 幂等键含 skill_version），
  旧 1.3 结果不复用——测试环境代价是"重新跑一遍初筛"，可接受。
