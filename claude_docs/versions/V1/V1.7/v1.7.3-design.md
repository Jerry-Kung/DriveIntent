# V1.7.3 设计：定级等级对外映射统一——H/A→high、B→medium、C→low

> 版本：V1.7.3 | 日期：2026-08-24

## 1. 背景与问题

Agent2（用户精筛定级）内部采用 H/A/B/C 四档定级（`UserLeadResult.lead_grade`），
对外 API 输出采用 high/medium/low 三档（`intent_level_code`）。此前两端靠
`app/api/mapping.py: _GRADE_MAP` 一一对应：

```
H → 高/high   (base 92, floor 85)
A → 中/medium (base 77, floor 70)
B → 低/low    (base 60, floor 50)
C → 无映射      → has_value=false（C 不在对外区间）
```

**问题一（转换规则不统一）**：内部 H 与 A 语义上都是高价值线索，却分别映射为
对外 high 与 medium；C 则直接无对外等级。对外对接方希望三档与内部四档有清晰、
统一的对应关系。

**问题二（内部审计依赖反推，不可持续）**：对外 API 落库时**只存映射后的
`intent_level_code`**，不存内部 HABC。内部审计/统计（`app/services/lead_results.py`）
靠 `_GRADE_FROM_CODE = {"high":"H","medium":"A","low":"B"}` 反推 HABC——
该反推能还原 HABC，**正是因为旧前向映射是一一对应的**。一旦前向映射改为
多对一，反推必然失真：

- `high` 无法区分本来是 H 还是 A；
- `low` 无法区分本来是 B 还是 C。

"对外三档 + 内部审计保留 HABC 四档"在仅改映射的假设下矛盾，必须打破"审计靠
反推"这条路。

## 2. 方案决策

### 2.1 前向映射：H/A→high、B→medium、C→low

```
H → 高/high   (base 92, floor 85)   保留原值
A → 高/high   (base 77, floor 70)   保留原值
B → 中/medium (base 60, floor 50)   保留原值
C → 低/low    (base 45, floor 40)   新增，低于 B 的 50
```

**决策点：base/floor 是否重排？** 不重排。对外三档从一一对应变成多对一后，
value_score 的 base/floor 仍绑定内部等级（H=92/85、A=77/70、B=60/50、C=45/40），
仅等级代码/中文标签按新三档输出。后果是各对外档位实际分数区间改变（见 §4.2），
这是"映射统一"的自然结果，不为对齐对外分档而改动内部评分逻辑。

### 2.2 内部审计不再靠反推：新增 `api_job.lead_grades` 列

`api_job` 新增 JSON 列 `lead_grades`，与 `result.results[]` 按下标一一对应，
记录每账号**真实内部 HABC**。审计/统计（`lead_results.py`）优先读该列；历史数据
（旧作业无此列，为 NULL）回退旧反推——旧映射一对一，反推仍然准确。

> 为什么落 `api_job.lead_grades` 而非塞进 `result`：`/jobs/{job_id}` 会把
> `result` 原样返回给外部调用方，`result` 即对外契约，塞内部字段会污染契约。

### 2.3 C 等级对外语义变化

C（base 45/floor 40）现进入 `_GRADE_MAP`。`has_value` 逻辑不变：
`bool(has_comments and out.is_valid_lead and mapped is not None)`。因此：

- 定级/复核为 C 且 `is_valid_lead=True` 的账号：首次出现 `has_value=True`、
  `value_score≈45`（截图缺失钳制到 floor 40）；
- 过滤命中（`build_filtered_lead_result` 置 `is_valid_lead=False`）与空评论账号：
  `is_valid_lead=False` / `has_comments=False`，仍 `has_value=False`。

审计侧（`lead_grades`/反推）仍以 HABC 呈现 C，不随对外"低"改变——满足"内部统计
和审计仍采用 HABC"。

## 3. 改动清单

### 3.1 `app/api/mapping.py`

- `_GRADE_MAP`：改为 §2.1 的新映射，注释说明"外部 code 已多对一，审计改读
  `api_job.lead_grades`"。
- `map_profile_result` 逻辑不变。

### 3.2 `app/models/api_job.py`

- 新增 `lead_grades: Mapped[list | None] = mapped_column(JSON)`（注释说明用途与
  历史数据回退）。

### 3.3 落库链路

- `app/api/agent2.py:run_profile_analysis`：新增 `grade_sink: list | None`，
  仿 `vision_sink` 按账号下标收集 `out.lead_grade`；except 分支补 `"C"` 保持对齐。
- `app/api/jobs.py`：`finish_job` / `finish_job_by_id` 新增 `lead_grades` 参数，
  非 None 时写 `job.lead_grades`。
- `app/api/worker.py`：`run_once` 建 `grades: list[str]`，经 `_execute` 传给
  `run_profile_analysis`，终态 `_finish` 传给 `finish_job_by_id`。

### 3.4 审计读取 `app/services/lead_results.py`

- `grade_of(acct, internal_grade=None)`：`internal_grade` 非空原样返回，否则回退
  `_GRADE_FROM_CODE.get(code, "C")`。
- `_to_row` / `lead_detail_data`：从 `job.lead_grades[index]` 取内部等级。
- `_GRADE_FROM_CODE` 注释更新（仅作旧数据回退）。

### 3.5 数据库迁移脚本

新增 `scripts/add_api_job_lead_grades.py`：幂等检测 + `ALTER TABLE api_job ADD
COLUMN lead_grades JSON`，仿 `scripts/add_llm_call_job_columns.py`。

## 4. 契约影响

### 4.1 对外 API 字段结构

`/api/v1/jobs/{job_id}` 的 `result.results[]` 字段（`intent_level`、
`intent_level_code`、`value_score` 等）**不变**，`lead_grades` 仅落 `api_job` 列，
不进 `result`。

### 4.2 对外等级三档语义与分数区间（`docs/DriveIntent-V1-API对接文档.md`）

| 等级代码 | 中文 | 分数区间 | 说明 |
|---|---|---|---|
| `high` | 高 | 70-92 | 含内部 H（85-92）与 A（70-77） |
| `medium` | 中 | 50-60 | 对应内部 B |
| `low` | 低 | 40-45 | 对应内部 C（V1.7.3 起对外） |

> 旧表 high 85-100 / medium 70-84 / low 50-69 废弃；新表为各档实际可输出分数范围。

### 4.3 内部审计/统计

仍以 HABC 四档呈现（`lead_grades` 提供真实等级；旧数据回退反推）。历史统计
口径（`docs/20260813-14_精筛定级等级分布统计.md`）不受影响。
