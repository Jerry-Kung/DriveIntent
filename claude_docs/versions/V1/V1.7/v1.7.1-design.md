# V1.7.1 设计：管理页面重构——线索列表对接测试环境实时精筛结果

> 版本：V1.7.1 | 日期：2026-08-17

## 1. 背景与问题

`http://<IP>:8000` 管理页面当前分三块：**分析任务**（`/`，Excel 本地上传 + V0
流水线进度）、**线索列表**（`/leads`，读 `Lead` 表）、**审计统计**（`/audit`，
只读 `api_job` / `llm_call_log`）。

测试环境实际跑的是**对外 API 异步路径**：对接方 `POST /api/v1/profile-analysis`
提交，`ApiJobWorker` 走「过滤 → 定级 → 审查 → 润色」产出结果写入 `api_job.result`
（`results[]`，每账号一条）。`Lead` 表在测试库中**没有数据**（V0 流水线停在
2026-07-20）。因此现有「线索列表」在测试库上是空的，无法用于审查精筛结果。

本版本重构管理页：撤销「分析任务」模块，让「线索列表」直接对接 `api_job` 的
实时精筛结果，并深入展示每条结果已持久化的处理链路内容。**不改任何业务流程**。

## 3. 范围决策

### 3.1 撤销「分析任务」模块（不改业务）

- 删除 Web 入口：`/`（index.html）、`/api/import`、`/api/analysis/start`、
  `/api/analysis/progress`、`/api/tasks/failed`、`/api/tasks/{id}/retry`。
- 导航「分析任务」移除，`/` 302 重定向 `/leads`。
- **保留** `app/importer/*`、`app/workflow/*`（V0 流水线）、`app/services/leads.py`
  的 `upsert_lead` 等代码不动——`app/api/agent2.py` 仍 import `app.workflow.pipeline`
  的共享符号（`USER_ANALYSIS_SKILL` 等），`app/main.py` 仍在 `WORKER_ENABLED` 下
  启动 V0 worker；删除会误伤业务路径。仅停用其 Web 触发入口。
- 删除对应测试：`tests/test_api_tasks.py` 中 import / start / progress / retry /
  index 相关用例。

### 3.2 线索列表页重建（数据源 = api_job）

- 每条 = `(job_id, account_uid)`，字段：等级（H/A/B/C）、`account_uid`（昵称仅
  详情页展示，因 `request_payload` 为 deferred 大列）、
  `value_score`、`is_car_owner`、`has_purchase_intent`、`profile_summary`、
  `processed_at`、`job_id`。
- **分页**：默认 20 条/页，账号级分页（见第 5 节）。
- **排序**：按作业完成时间 `finished_at` 倒序（最新在前）。同一 job 内按
  `results[]` 数组顺序（同 job 各账号 `processed_at` 相同，见 `agent2.py:88`）。
- **日期筛选**：按 `finished_at` 的**东八区自然日**筛选，复用
  `app/services/audit_stats.py:17` `utc_range` 的 UTC→东八区口径。
- **等级筛选**：H / A / B / C 下拉（含「无价值 C」），便于审查时聚焦高价值。
- **详情链接**：进入第 3.3 节详情页。

### 3.3 线索详情页重建（整链路已持久化内容）

用户确认「只展示已持久化内容」，故详情页展示下列**精确**与**近似**两类：

**精确（账号级，来自 `api_job`）**：
1. **输入**：`request_payload.accounts[i]` 的昵称 / 抖音号 / 评论历史（逐条
   视频标题 + 评论内容 + 时间 + 点赞）/ `homepage_vision_text`（识图文本）。
2. **输出**：`result.results[i]` 全字段（`intent_level_code` / `value_score` /
   `profile_tags` / `profile_summary` / `analysis` / `is_car_owner` /
   `has_purchase_intent` / `processed_at` / `error`）。
3. **作业元信息**：`job_id` / `status` / `created_at` / `finished_at` / 进度。

**近似（作业级，来自 `llm_call_log`）**：
- 该 job 处理时段内的 LLM 调用明细，每条含 `skill_id` / `skill_version` /
  `prompt_version` / `model_name` / tokens / `duration_ms` / `error` /
  `output_text`（截断展示）。这是「该 job 处理时所使用的后端代码版本」的
  真实记录（满足需求第 8 条，见第 7 节）。
- **必须明示局限**：`llm_call_log` 无 `job_id` / `account_uid` 外键，只能按
  `created_at` 落在 `[job.created_at, job.finished_at]` 窗口内近似关联；多 worker
  并发时窗口会重叠，无法精确到「单个账号的某次调用」。页面上标注「作业级近似」。

**不展示（未持久化）**：`baseline_grade` / `match_adjustment` /
`profile_adjustment` / `review_action` / `review_tier` / `analysis_polish` /
`filter_category` 等**内部审计字段**——`agent2.py` 的 `run_profile_analysis` 走完
链后仅经 `map_profile_result` 转成对外 `ProfileResult` 写入 `result`，这些字段
只在内存中、未落库（对比 V0 流水线 `pipeline.py:149` 会 `save_result` 存完整
`UserLeadResult`）。按用户「只展示已持久化内容」的决策，本期不新增落库、不展示。

### 3.4 人工审核：本期不做（已确认）

- 原需求「保留人工审核」与「导出默认仅审核」随审核机制一并**延后**。
- 现有 `/api/leads/{id}/review` 端点与 `Lead.review_*` 字段保留不动（V0 路径），
  但新线索列表无审核入口。
- 本期**导出为全量**（不按审核状态过滤）。

### 3.5 审计统计页 `/audit`

保留不动。它已只读 `.env` 配置的库（即测试库），满足「审计数据页面只对接测试
环境数据库」。

## 4. 数据访问层

新增 `app/services/lead_results.py`，提供账号级分页查询与导出。**不动** `Lead`
表相关的 `app/services/leads.py` 现有函数（V0 路径仍用）。

### 4.1 查询形状

- 过滤：`job_type='profile_analysis'`、`result IS NOT NULL`、可选 `finished_at`
  落在东八区日期范围、可选 `status IN ('success','partial')`。
- 排序键：`finished_at DESC, id DESC`（作业级）。job 内按 `results[]` 顺序。

### 4.2 分页策略（账号级，20/页）

`result` 是 JSON 列，账号级分页不能在 SQL 层对结果内字段直接 `ORDER BY/LIMIT`。
采用**作业级游标 + 内存扁平化切片**，避免全量读大 JSON 列：

1. SQL 查候选 job 的 `(id, finished_at, JSON_LENGTH(result->'$.results'))`——只取
   账号数，不读 result 大列。`JSON_LENGTH` 需方言分派（MySQL `JSON_LENGTH` /
   SQLite `json_array_length`，参照 `audit_stats.py:37` 的方言分派模式）。
2. 按 `finished_at DESC` 从头累计账号数，定位覆盖 `[(page-1)*size, page*size)`
   的那段 job 子集。
3. 只读这段 job 的 `result` 列，Python 扁平化为账号级列表（带 `job_id`、
   `finished_at`、数组下标）。
4. 切片取当页，返回 `{total, page, size, rows}`。`total` = 累计账号总数。

**等级筛选时的退化**：等级在 JSON 内，无法作业级 SQL 过滤。启用等级筛选时
退化为「全量扁平化 + Python 过滤 + 内存分页」（审查场景低频，量级可控——
14,823 账号的 `result` 合计约 10~20MB，远程读有数秒延迟，属可接受；必要时
后续加缓存或 MySQL `JSON_TABLE` 升级，本期不做）。

### 4.3 导出

CSV 复用既有 `_csv_safe`（防公式注入），列改为 api_job 源字段：`account_uid`、
等级、`value_score`、`is_car_owner`、`has_purchase_intent`、`profile_summary`、
`profile_tags`、`analysis`、`processed_at`。昵称不在列表/导出中（仅详情页展示，
因 `request_payload` 为 deferred 大列）。本期无审核过滤，导出命中当前筛选的
全部账号。**导出仅 CSV，下线 HTML 导出，删除 `export_leads.html`。**

- 不删 V0 流水线与 importer 代码（仅停用 Web 入口）。

- 不动 `/audit` 审计统计页。

## 9. 观察点与遗留

- **LLM 明细精确关联（已修复）**：V1.7.1 补丁为 `llm_call_log` 增加 `job_id`/`account_uid`
  两列，worker 经 ContextVar 全链路透传落库，详情页按 `(job_id, account_uid)` 精确匹配
  （历史数据回退时间窗）。迁移脚本 `scripts/add_llm_call_job_columns.py` 已执行。
- **全量扁平化性能**：等级筛选触发的全量读约 10~20MB，远程数秒；数据量继续
  增长后可加缓存或 `JSON_TABLE`。
- **测试库 MySQL 版本**：游标分页仅需 `JSON_LENGTH`（MySQL 5.7+ 支持），无需
  `JSON_TABLE`；版本风险低。
