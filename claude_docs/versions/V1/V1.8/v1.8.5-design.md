# V1.8.5 设计：评论初筛空 content 评论剔除——index 映射错位修复

> 版本：V1.8.5 | 日期：2026-09-03

## 1. 背景

2026-09-03 审计页观察评论初筛大量失败，后端日志无 ERROR、LLM 消耗明细无失败。
实盘库统计（当日 UTC）：comment_screening 共 450 单，**success 164 / failed 199 /
pending 87**，partial 0。

### 1.1 证据链

1. 199 个失败作业**全部**含 1 条 `content` 为空的评论；逐条 `result.results[].error`
   均为 `"初筛输出 index 集合不完整：期望 [0, 1, 2]，实际 [0, 1]"`。
2. 每个失败作业日志显示 6 次 LLM 调用（3 次 video_context + 3 次 screening），
   全部 HTTP 200、`llm_call_log.error` 为 None——失败不在 LLM 调用层。
3. 用库内历史 LLM 原文重放 `run_comment_screening`：异常定点抛在
   `map_batch_result` 的 index 集合校验（`实际 [0, 1]` 缺第 3 条）。
4. 失败集中于同一视频（`恭喜你中了500万彩票，这两台车你怎么选`）的同一组 3 条评论
   （含一条空 content），被对接方反复提交，失败数持续累积；87 个 pending（attempt=2/3）
   按同路径会继续失败。

### 1.2 根因

廉价 LLM（qwen3.7-flash）对批次内 `content=""` 的条目不输出对应 item：
3 条（1 空）的批，模型只回 `items[]` 的 index `[0,1]`——空内容无可分析文本，被
跳过。而 V1.7.2 设计在 `map_batch_result` 用**严格集合校验**兜底（index 须恰等
`{0..n-1}`，任何缺失即抛 `ValueError`），此处 n=3 而实际只回 {0,1}，校验失败。

该 `ValueError` 抛在 `_screen_batch` 调 `map_batch_result` 处（`agent1.py`），
**在 `SkillExecutor` 的解析/校验重试循环之外**（`executor.run` 内部的解析/校验
错误才会被其重试），所以直接冒泡到 `run_comment_screening` 的通用 `except`，批内
每条评论被标 `error`；整批全错 → 作业级 `fail_or_retry`，3 次重试用尽后
`status=failed`。

这是数据边界情况与 V1.7.2 严格校验的碰撞，非代码回归。V1.7.2 设计文档
（§1 背景）已复用 8000 路径的"集合校验 + 拆半重试"；本次问题发生在**空内容**，
非 ID 转录错误，拆半重试对"模型永远跳过空 content"无效——重试只是再抛同一枚
错位硬币。

## 2. 方案决策：空 content 由代码层剔除并合成结果

沿用 V1.7.2 的核心理念——**不需要 LLM 参与的东西交给确定性代码**。空 content
评论可分析性为零，不应当作 LLM 一条判定对象，也不应因它让整批失败。

- **输入侧**：`build_screening_input` 过滤掉空 content（None/空白/纯空白）评论，
  只对非空评论重新编 index（0..k-1，k=非空条数）。
- **输出侧**：`map_batch_result` 为被剔除的空 content 评论合成确定性结果
  （`comment_actor=off_topic`、`is_meaningful=false`、`has_purchase_intent=false`、
  `reason="评论内容为空，无可分析文本"`），并保持返回 items 与输入一一对应。
- **index 校验范围**：期望集合变为 `{0..k-1}`（k=非空条数），非空评论的 index
  仍严格校验；空评论永远不经过模型。

### 2.1 判定标准

`_is_no_content(content)`：`None`、空串、纯空白串一律视为无可分析文本。与
`CommentObject.comment_content`（`str`，API 路径）和 `Comment.content`
（`Text`，V0 路径）的存储形态一致。

### 2.2 合成结果语义

`comment_actor=off_topic` 使 `resolve_filter_type()` 判为不过筛（filter_type 与
真实 `comment_actor` 严格一一对应，V1.3 规则），空内容评论天然不该进下游线索。
`confidence=0.0` 表示无模型证据。理由字段可供审计/排查。

## 3. 改动清单

### 3.1 `app/skills/screening_batch.py`（唯一实质代码改动）

- 新增 `_is_no_content()` 与 `_empty_comment_kwargs()`。
- `build_screening_input`：过滤空 content 后编 index，`comment_count` 为非空条数。
- `map_batch_result`：签名由 `comment_ids` 改为 `comment_pairs`
  （`[(comment_id, content), ...]`，须与 `build_screening_input` 入参一致），
  保留 index 集合校验（期望 `{0..k-1}`），空评论合成结果、非空评论按位置映射。

### 3.2 两条路径接入（仅调用点签名适配，无逻辑变化）

- `app/api/agent1.py:_screen_batch`：`pairs = [(c.comment_id, c.comment_content) ...]`
  → 传 `pairs`；返回 `{i.comment_id: i}` 不变。
- `app/workflow/pipeline.py:_call_screening`：`pairs = [(str(c.id), c.content) ...]`
  → 传 `pairs`。

### 3.3 Prompt/schema/SKILL_VERSIONS

**全部不升**。本次是纯代码层对"空内容"这条数据边界的处理，不改变喂给 LLM 的
Prompt 文本、不改变输出契约字段、不改变 Skill 行为参数。按 VERSIONING.md §4，
`comment_lead_screening` 的 `1.8.3` 版本号保持不变——升版本会触发 V0 聚合路径按
`SKILL_VERSIONS` 丢弃历史重筛，此处无必要。

### 3.4 测试

- `tests/test_comment_screening.py`：新增
  `test_screen_batch_skips_empty_content_comment`（V0 路径空 content 剔除 + 合成结果）。
- `tests/test_agent1.py`：新增
  `test_screening_empty_content_comment_not_failed`（线上事故形状：3 条含 1 空、
  模型只回 [0,1]，作业成功且只用 1 次 screening 调用，不因重试烧 3 次）。

## 4. 影响范围

- **对外 API 契约**：无变化。请求仍可含空 content 评论；响应结构、字段、
  语义不变（空评论得到 `passed=false` 的常规结果，非报错）。
- **存储**：无迁移。`api_job.result` / `AnalysisResult.result` JSON 结构不变。
- **LLM 调用次数**：含空 content 的批从"每次全失败重试 3 次（3×N 次调用）"降为
  "一次成功（1 次调用）"——本次事故每个失败作业 6 次调用可省为 2 次。
- **历史数据**：199 个 failed / 87 个 pending 作业为存量数据，本次不自动重跑。
  是否重跑由运维决定；pending 作业（attempt=2/3）在修复后的 worker 上认领会
  走新逻辑，成功。
- **版本级联**：无。无 Prompt/Skill 版本变更。

## 5. 验证

- 全量 pytest：**356 passed**（基线 354 + 新增 2）。
- 端到端复现（只读重放库内历史 LLM 原文）：5 个线上失败作业修复后均 1 次
  video_context + 1 次 screening 调用即成功，0 错误；空 content 评论得
  `off_topic` 不过筛，两条非空评论正确映射（含真实询价者 `passed=true`）。
