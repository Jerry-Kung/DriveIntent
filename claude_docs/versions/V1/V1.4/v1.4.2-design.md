# V1.4.2 补丁设计：连接池耗尽根因修复（线程池收敛 + 截图只收 URL）

> 版本：V1.4.2 | 日期：2026-08-05

## 1. 背景

V1.4.1 之后，生产/测试环境仍持续报：

```
sqlalchemy.exc.TimeoutError: QueuePool limit of size 15 overflow 15 reached,
connection timed out, timeout 30.00
```

栈顶为 `app/workflow/worker.py:70` → `run_once` → `app/workflow/tasks.py:31` `claim_next`。
即 **worker 抢不到连接**。此前已做过的两个补丁（轮询不搬运大列、LLM 调用期间释放连接、
停滞作业兜底）均未消除该报错，说明先前定位的都不是根因。

## 2. 根因（已复现）

### 2.1 主因：Web 线程池容量 > 数据库连接池容量

- 项目所有对外端点（`app/api/routes.py`、`app/web/routes.py`、`app/web/audit.py`）
  都是**同步 `def`** 端点，FastAPI 将其派发到 anyio 默认线程池执行。
- 每个在途请求经依赖 `get_db()` 取得一条 DB 连接，**持有到请求结束**。
- 本环境 anyio 默认线程池 `total_tokens = 40`，而连接池容量
  `pool_size(15) + max_overflow(15) = 30`。
- 因此并发请求数最多可达 40 > 30：第 31 个及以后的请求在 `pool.connect()` 上阻塞，
  直到 `pool_timeout=30s` 抛 `TimeoutError`；同时**两个 worker 与之抢同一个池**，
  worker 的 `claim_next` 成为受害者——这正是用户看到的栈。

复现：`scripts/diag_pool_repro.py` 用容量 30 的 QueuePool + 40 并发同步请求，
得到 30 成功 / 10 超时，且模拟 worker 的 claim 抛出**同一条**错误消息。

### 2.2 放大因素：Base64 截图使单作业 payload 达 25MB

生产数据实测（2026-08-05）：

| 指标 | 值 |
|---|---|
| profile_analysis 请求体均值 | 13.15 MB |
| 单作业最大 | 24.98 MB |
| 截图占 payload 体积 | 99.9% |
| 待处理作业 payload 合计 | 4.30 GB |
| `api_job` 表体积 | 6407 MB |
| 账号截图字段形态 | 641/641（100%）为 `data:` base64，0% 为 URL |

提交端点在写这条大行期间长时间持有连接，直接拉长每个请求的连接占用时长，
把 2.1 的失配从"偶发"变成"持续"。

### 2.3 已排除的假设（有证据）

- **连接泄漏 / 长事务**：`information_schema.processlist` 观察到应用连接均为
  `Sleep`、`active=0`，连接年龄正常轮换 → 无泄漏。
- **进程反复重启**：连接年龄未归零 → 未重启。
- **claim SQL 慢**：EXPLAIN 命中 `ix_api_job_status_order`，0.03s。
- **大 payload 解析阻塞事件循环**：实测 24.31MB `json.loads` 仅 0.059s，
  Pydantic 校验 0.000s → 可忽略，该假设被自己的测量推翻。

## 3. 修复方案

### P0-1：显式收敛 anyio 线程池（配置 + 启动时应用）

- 新增配置 `WEB_THREADPOOL_SLOTS`（`settings.web_threadpool_slots`，默认 20）。
- `app/main.py` 新增 `_apply_threadpool_limit()`，在 `lifespan` 首行调用：
  `total_tokens = min(web_threadpool_slots, pool_size + max_overflow)`，
  超出容量时下调并 WARNING。
- 启动日志打印连接池 size/overflow/容量与实际线程池槽位，便于运维核对。
- 默认 20 < 容量 30，为两个 worker 留出 10 条余量。

### P0-2：`account_homepage_screenshot` 只接受 URL（**对外契约变更**）

- `app/api/schemas.AccountObject` 增加 `field_validator`：空串放行（既有降级路径），
  `http://` / `https://` 放行，其余（base64 / `data:` URI）抛校验错误 → `422`。
- `app/skills/vision.build_image_message` 删除 `_to_image_url` 的 data-URI 包装，
  URL 直接透传给多模态模型，由模型侧自行拉取。
- `app/api/jobs._strip_screenshots` 逻辑不变，仅改注释：新作业字段已是短 URL，
  该函数今后只服务存量含 base64 的历史行。

**已知影响（用户已确认接受）**：生产流量当前 100% 传 base64，对接方改造完成前
`POST /api/v1/profile-analysis` 将全量返回 `422`。对接文档已同步修订（见第 5 节）。

## 5. 未纳入本补丁的观察（留待决策）

- **P1 吞吐**：积压 1465 条 pending，最长等待 732 分钟；worker LLM 实测并发 7.05 ≈
  配置 8（已饱和），提高 `API_WORKER_CONCURRENCY` 可提吞吐，但需先确认上游 LLM 配额。
  08-04 16:00 ~ 08-05 01:00 (UTC) 上游 LLM 单次调用均值 396~670 秒，是积压主因。
- **P2 405**：`GET /api/v1/jobs/{job_id}` 未注册 HEAD，Starlette 返回 405（行为正确）。
  值得注意的是紧随其后的 `GET` 返回 **401**——这些轮询方持有无效 API Key，
  永远取不到结果却持续占用线程池槽位与连接。建议联系对接方核对 Key。
- **P3 存量**：206 条终态作业仍带未剥离的 base64 payload；`api_job` 表 6407MB
  可考虑离线清理。
- **MySQL 侧**：`Max_used_connections=152` vs `max_connections=151`，
  连接上限曾被打满，**扩大连接池前需先提升 MySQL `max_connections`**。
