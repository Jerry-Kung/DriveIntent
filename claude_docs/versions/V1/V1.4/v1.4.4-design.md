# V1.4.4 设计：事件循环解阻塞 + 截图不入库（识图文本化存储）

> 版本：V1.4.4 | 日期：2026-08-05 | 类型：补丁版（架构级：存储模型 + 处理时序）

## 1. 背景与问题

V1.4.3 上线后，测试环境仍持续报 `QueuePool limit of size 15 overflow 15 reached, connection timed out, timeout 30.00`。V1.4.3 修复的是「Worker 在 LLM 期间持有连接」——这是真实缺陷，但不是本次报错的成因。

本版基于**实测**（非推断）定位根因并重构存储模型。

### 1.1 根因：同步大读取冻结事件循环

`claim_next_job_detached()` 在认领作业时必须一次性读出 `request_payload`。实测数据：

| 测量项 | 实测值 | 来源 |
|---|---|---|
| pending 队列 `profile_analysis` | **538 行，payload 平均 12.98MB，最大 25.0MB** | 测试库直查 |
| 远程 MySQL 读一条 22.7MB payload | **3233–3656ms** | 一次性诊断脚本（问题闭环后已删除） |
| 该读取期间事件循环心跳 | **5 次**（应约 365 次） | 同上 |
| 事件循环最大单次停顿 | **3657ms** | 同上 |

这次读取是**同步 IO，直接跑在 asyncio 事件循环里**。执行期间整个 loop 被完全冻住：其余 11 个 Worker 协程、reaper、以及所有 HTTP 请求处理全部无法推进。

`API_WORKER_CONCURRENCY=6` + `WORKER_CONCURRENCY=6` = 12 个协程，各自轮流对一个 538 深、平均 12.98MB 的队列做这件事 → 事件循环长期处于冻结状态。

冻结的连锁后果：

1. FastAPI 同步端点跑在 anyio 线程池，轮询请求取走连接后，需要回到事件循环才能完成响应并归还连接 —— loop 冻住则连接**只出不回**。
2. Worker 自身也抢不到连接 → `QueuePool` 超时。
3. **超时等待（30s）本身也是同步阻塞**，进一步冻住 loop。

这解释了日志的三个反常特征，构成完整证据链：

- 07:33:33 之后 LLM 调用**完全归零**（loop 冻死，协程无法推进）
- 报错呈 **30.00s 精确串行间隔**（协程只能挨个进入同步超时，无法并发）
- 07:35:03 五个请求在**同一毫秒齐发**（解冻瞬间积压集体恢复）

### 1.2 已排除的假设（勿重复排查）

| 假设 | 排除依据 |
|---|---|
| anyio 线程池耗尽 | 峰值 checkedout=5，0 超时 |
| 401 无效 Key 轮询消耗连接 | 401 在取连接前被拦下，消耗 0 连接；`/health`、HEAD 同样为 0 |
| 业务 Worker 在 LLM 期间握连接 | 真实 pipeline 采样，checkedout 峰值 = 0 |

> 上述结论由一次性诊断脚本实测得出，问题闭环后脚本已删除；结论本身仍然有效，
> 后续排查**不要重复验证这三条**。事件循环不被阻塞这一性质已由回归测试
> `tests/test_event_loop_not_blocked.py` 长期守护。

### 1.3 数据层面的放大器

| 项 | 实测 |
|---|---|
| `api_job` 表体积 | **6408 MB**（10093 行） |
| 其中 `request_payload` 合计 | **9520 MB** |
| 其中 `result` 合计 | 78 MB |
| payload > 500KB 的行 | 757 行，平均 11906KB，最大 25.0MB |
| 分状态大 payload | failed 7 / partial 24 / **pending 560** / running 9 / success 178 |

即：表体积的 99% 是 base64 截图，且**大头压在 pending**（待处理业务数据，非死数据）。

## 2. 决策与目标

用户决策（本设计的既定前提，不再论证）：

> 数据库不存 base64 原始截图，所有图片类数据统一使用项目当前的识图 Skill 解析为纯文本后以文本方式存储到数据库。**API 接口不动**，存量数据（6408MB）全部清理。

三项细化决策：

| 议题 | 决策 |
|---|---|
| pending 队列 | **先跑完再清理**——新逻辑上线后让 Worker 正常消费 538 个 pending，再清理历史终态行。业务数据零丢失 |
| 识图失败处置 | **降级为无截图继续**——与现行 `recognize_screenshot` 一致：告警、`vision_text=""`、走无截图评级路径、作业 `status=success` |
| 识图时机 | **Worker 认领后立即识图**——POST 仍接收 base64 但不落库，立即返回 202；Worker 认领 → 识图 → 存文本 |

本版两条独立且都必要的主线：

- **主线 A（止血，直接修复当前报错）**：所有同步 DB IO 移出事件循环。
- **主线 B（治本，消除大列）**：base64 不入库，改存识图文本。

两者不可互相替代：A 解决"冻结"，B 解决"为什么有 13MB 要读"。即使 B 让 payload 回落到 KB 级，A 仍是必须坚持的纪律（远程 MySQL 抖动、result 增长同样会阻塞 loop）。

## 3. 主线 A：同步 DB IO 移出事件循环

### 3.1 原则

**在 async 函数体内，任何 DB 调用都必须经 `asyncio.to_thread()` 执行。**

Worker 协程与事件循环共用一个线程；同步 DB 调用的等待时间（网络往返、大列传输、`pool_timeout` 排队）全部计入 loop 冻结时长。

### 3.2 改造点

| 位置 | 现状 | 改为 |
|---|---|---|
| `app/api/worker.py: run_once` 会话1 认领 | 直接调 `claim_next_job_detached` | `await asyncio.to_thread(...)` |
| `app/api/worker.py: run_once` 会话2/3 落状态 | 直接调 `fail_or_retry_by_id` / `finish_job_by_id` | `await asyncio.to_thread(...)` |
| `app/api/worker.py: _execute` 的 `cb` | 同步 `set_progress_by_id` | 改为 async 回调，内部 `await asyncio.to_thread(...)` |
| `app/api/worker.py: reap_stale_once` | 同步 `fail_stale_running_jobs` | `await asyncio.to_thread(...)` |
| `app/workflow/worker.py: run_once` | 同步 session 全流程 | 同规则包装 |

### 3.3 进度回调的契约变更（跨模块）

`progress_cb` 由同步回调改为 **async 回调**，调用点相应改为 `await progress_cb(done)`：

- `app/api/agent1.py: run_comment_screening`
- `app/api/agent2.py: run_profile_analysis`

这是内部契约，不影响对外 API。

### 3.4 验收

新增回归测试 `tests/test_event_loop_not_blocked.py`：在事件循环中跑一个心跳探针（`asyncio.sleep(0.01)` 计数），同时驱动 Worker 完成一个作业；断言**最大单次停顿 < 200ms**。当前代码下该测试必然失败（红），改造后转绿。

## 4. 主线 B：截图不入库，改存识图文本

### 4.1 时序（新）

```
POST /api/v1/profile-analysis（契约不变，仍收 base64）
  ├─ 抽出各账号 base64 → 写入文件暂存区 data/staging/<job_id>.json
  ├─ payload 中 account_homepage_screenshot 置 ""      ← 不落库 base64
  └─ 落 api_job（KB 级）→ 立即返回 202

Worker 认领（payload 仅 KB，读取成本消失）
  ├─ 从暂存区读回 base64
  ├─ 逐账号 recognize_screenshot() → 纯文本画像
  ├─ 文本参与评级（原路径不变）
  └─ 终态：识图文本写回 payload.accounts[i].homepage_vision_text
           + 删除暂存文件
```

### 4.2 截图暂存区（用户决策中标注"需解决"的子问题）

这是"POST 不落库 base64"与"Worker 认领后才识图"之间的必然缺口：截图必须在**提交与认领之间**存活，且要能跨进程重启。

**方案：宿主机挂载的文件暂存区。**

| 项 | 设计 |
|---|---|
| 路径 | `settings.screenshot_staging_dir`，默认 `data/staging` |
| 文件 | 每作业一个 `<job_id>.json`，内容 `{"<account_index>": "<base64>"}` |
| 写入 | POST 端点内（同步 `def`，跑在 anyio 线程池，不阻塞 loop） |
| 读取 | Worker 认领后经 `asyncio.to_thread` 读取 |
| 删除 | 作业进入**终态**时删除；`pending`/`running`（含重试）期间保留 |
| 孤儿回收 | 启动时扫描暂存目录，删除无对应 `pending`/`running` 作业的文件 |
| 持久化 | `docker-compose.yml` 增加 `- ./data:/app/data`（可写，区别于只读的 `./config`） |

**容量约束（必须写入部署文档）**：峰值磁盘占用 ≈ 队列深度 × 单作业截图体积。按当前 538 深 × 12.98MB 估算约 **7GB**。部署机需预留 ≥ 20GB 可用空间。

**重试语义**：重试时暂存文件仍在，会重新识图（重复一次 LLM 成本）。选择不做"识图文本随进度增量回写"以避免为省成本而增加 DB 写次数；此代价可接受且有界（`max_attempts` 封顶）。

**失败模式**：暂存文件缺失（人工清理、磁盘故障）时，按既定决策**降级为无截图继续**——与识图失败同路径，告警 + `vision_text=""`，不使作业失败。

### 4.3 落库的文本形态

终态写回 `payload.accounts[i].homepage_vision_text`（纯文本 / 识图 JSON 字符串，KB 级）。保留可追溯性：事后仍能查到"当时从截图里读出了什么"，但不再有 base64。

`account_homepage_screenshot` 字段在库内**恒为 `""`**。

### 4.4 存量兼容（关键）

538 个存量 pending 的 payload 里**已经带着 base64**。新逻辑必须兼容：

> Worker 认领后，若 `payload.accounts[i].account_homepage_screenshot` 非空，**直接使用它**，不去暂存区找。

即暂存区是"新作业"的路径，内联 base64 是"存量作业"的路径，两者在识图入口处二选一。存量跑完后该分支自然失效（但保留，成本为零）。

### 4.5 对外契约

**完全不变。** `AccountObject.account_homepage_screenshot` 仍接收 base64；`GET /api/v1/jobs/{job_id}` 响应结构不变。这是 V1.4.2 被回退的教训——不做破坏性契约变更。

## 5. 存量数据清理（阶段化）

按"先跑完再清理"决策，分三阶段，**不可提前**：

| 阶段 | 动作 | 前置条件 |
|---|---|---|
| 一 | 部署新代码，Worker 正常消费 538 个 pending | 主线 A + B 上线并验证 |
| 二 | 清理历史**终态行**（success/failed/partial）的 `request_payload` 大字段 | pending 队列排空 |
| 三 | `OPTIMIZE TABLE api_job` 回收物理空间 | 阶段二完成，且选业务低峰 |

清理脚本 `scripts/cleanup_api_job_payload.py`：

- 只处理终态行，**绝不触碰 pending/running**
- 只清空 `request_payload` 中的 base64 字段，**保留 `result`、`status`、时间戳、`progress_*`** —— `/audit` 页面依赖这些列做统计（10093 行，2026-07-24 ~ 2026-08-05）
- 分批提交（如 200 行/批）避免长事务
- 默认 dry-run，显式 `--apply` 才写入

## 6. 运维项（代码不可解决）

实测 MySQL 侧：

```
max_connections      = 151
Max_used_connections = 152      ← 已打满
```

连接数上限已被触顶，且这与应用池容量（15+15=30）不匹配，说明存在其他消费者或多实例。**需运维侧确认并上调 `max_connections`**（建议 ≥ 500）。此项独立于本版代码改动，不因代码修复而消失。

## 8. 风险

| 风险 | 缓解 |
|---|---|
| 暂存目录未挂载 → 重启丢截图 | 启动时校验目录可写，不可写则 fatal 日志；文档明示挂载要求 |
| 磁盘写满 | 容量估算写入部署文档；终态即删 + 启动孤儿回收 |
| `to_thread` 改造遗漏某处 | 心跳回归测试兜底（3.4 节），停顿超阈值即失败 |
| 清理脚本误删业务数据 | 默认 dry-run；只碰终态行；保留 audit 依赖列 |
