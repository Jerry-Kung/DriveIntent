# V1.4.5 设计：LLM 调用日志落库移出事件循环（连接池耗尽放大器修复）

> 版本：V1.4.5 | 日期：2026-08-05 | 类型：补丁（bugfix，无对外契约变更）

## 1. 背景

V1.4.3 / V1.4.4 之后测试环境一度"未再观察到 `QueuePool limit reached`"，
判定闭环并以 851348c 收尾。**2026-08-05 12:16 起报错复发**——本次 22672 行
日志中出现 **149 次** `QueuePool TimeoutError`。上一轮的闭环结论被推翻。

## 2. 根因

### 2.1 现象：日志静默间隔是 `pool_timeout` 的整数倍

对带时间戳的行做间隔分析，18 处 ≥25s 的静默：

```
30.0s / 30.0s / 30.0s / 30.0s / 30.0s / 30.0s / 30.0s / 150.1s
30.0s / 30.0s / 90.1s / 30.0s / 120.0s / 30.0s / 150.1s / 30.0s / 150.1s / 32.0s
```

30.1s ≈ `DB_POOL_TIMEOUT=30`，90.1s ≈ 3×30，120.0s ≈ 4×30，150.1s ≈ 5×30。
**18 处中 17 处静默前最后一行是 `httpx: POST .../chat/completions 200 OK`**——
即 LLM 调用刚返回、正要写日志的那一刻。这不是巧合：事件循环在"取连接写
LLM 日志"这一步被同步阻塞满 pool_timeout，期间所有协程与 HTTP 请求停摆。

### 2.2 真因：`LLMGateway._log` 是同步函数，却被 `async def chat` 直接调用

`app/llm/gateway.py`：每次 LLM 调用成功或失败，`_log` 都要
`session_factory()` 取一条连接、写一行（`input_digest` 2000 字符 +
`output_text` 8000 字符）、commit——**全程同步，跑在事件循环里**。

- 池有富余时：慢写只是把事件循环拖慢几十毫秒，不易察觉；
- **池接近耗尽时：`pool.connect()` 在事件循环内同步阻塞满 30s**，
  期间所有协程与 HTTP 请求停摆 → 更多请求超时 → 池进一步被占 → 正反馈。

### 2.3 为何此调用点从未出现在报错清单里

`_log` 末尾是 `except Exception: pass`，池耗尽时它抛的 `TimeoutError`
被**原地吞掉**。149 次报错的 traceback 调用点全部是受害者：
`get_job` 119 次、`set_progress_by_id` 19 次、`claim_next` 11 次。
V1.4.4 收尾时正是被这份"报错清单"带偏，把结论做成了"已闭环"。

### 2.4 量级：全系统最高频的 DB 写入，为何 V1.4.4 验证期"看起来好了"

- 3 小时 `llm_call_log` 写入 **6703 行** vs API 作业 246 个 ≈ **27 倍**；
  6 个 API worker × 每作业多次 LLM 调用（识图 + 用户分析 + 重试），
  任何时刻都有大量日志写库请求。
- V1.4.4 闭环验证期的流量模式与本次不同（本次 3 小时 274 comment + 158
  profile 密集提交），池一直处于贴顶状态，30s 冻结被放大成可见故障。

### 2.5 与 V1.4.4 的关系（勿重复调查）

V1.4.4 修的是**认领时读一次** 13MB payload 的同步调用；
`_log` 是**每次 LLM 调用都发生**的另一处同步 DB 写入点，被"把 worker
三段会话搬进 to_thread"的整体改造漏掉。两类是同一 bug 类的不同实例。

## 3. 设计目标

1. LLM 日志落库不得阻塞事件循环（连接池耗尽时也不得同步等 30s）；
2. 落库失败仍被吞掉，日志是旁路、不影响主流程；
3. 零对外契约变更；可回归验证（先复现、后修复）。

## 4. 方案

### 4.1 核心改动：`_log` 拆为同步体 + async 包装

```
_log_sync(**kw)   # 原同步体，不动逻辑
async _log(**kw)  # asyncio.to_thread(lambda: _log_sync(**kw))
                  # 异常同样吞掉（线程内抛出，await 侧捕获）
```

`chat` 的成功/失败两个调用点改为 `await self._log(...)`。

### 4.2 改动清单

| 文件 | 改动 |
|---|---|
| `app/llm/gateway.py` | `_log` 拆分为 `_log_sync`（同步体）+ `async _log`（to_thread）；`chat` 两处调用点改 `await` |
| `tests/test_llm_log_not_blocking.py`（新增） | 心跳探针复现：单次 `gateway.chat` 期间事件循环不得冻结（模拟日志写库 0.3s 延迟）；另断言落库异常仍被吞掉不影响业务 |

### 4.3 边界

- 每条日志一次 to_thread 调度，开销可忽略（异步路径本就无阻塞诉求）；
- 连接数不变：日志仍占 1 条短连接，但不再在事件循环内等它。

## 5. 验证结果

1. **失败测试先行**：修复前实测 `max_stall=616ms`（上限 200ms）FAIL，
   修复后通过——证明测试确实锁住了这个 bug。
2. **全量回归**：`250 passed`，仅剩既有无关失败
   `tests/test_config.py::test_api_worker_defaults`（读真实 .env 的
   `API_WORKER_CONCURRENCY=6`，与本次改动无关）。
3. **证据链小结**：30s 倍数静默 ×18、17/18 前置 LLM 返回、日志 27× 作业量。

### 上线后观察项

- `QueuePool limit reached` 是否消失（关键指标）；
- 日志中 30s 倍数的静默间隔是否消失（该模式是本 bug 的指纹）。

## 6. 遗留事项（不在本版本）

- **MySQL `max_connections=151` 已打满**（`Max_used_connections=152`，峰值
  出现在 2026-06-02；`Connection_errors_max_connections=38` 为 133 天累计，
  **非本次故障的直接成因**——本次直接成因是事件循环冻结）。调大步骤
  （含文件描述符 `LimitNOFILE` 的坑）已写入部署文档 §7，属运维侧执行；
- **P2** `/api/v1/jobs/{job_id}` 增加 HEAD 支持（当前返回 405，本次日志
  240 次 HEAD 405——对接方在用 HEAD 探活，有真实流量佐证）；
- V1.3 → V1.4.5 各版本待合入 `main`。
