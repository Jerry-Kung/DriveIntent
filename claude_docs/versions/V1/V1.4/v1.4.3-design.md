# V1.4.3 设计：API Worker 会话生命周期修复（连接池耗尽根因）

> 版本：V1.4.3 | 日期：2026-08-05 | 类型：补丁（bugfix，无对外契约变更）

## 1. 背景

`QueuePool limit of size 15 overflow 15 reached, connection timed out, timeout 30.00`
在测试环境持续复发。V1.4.2 曾尝试修复（收敛 anyio 线程池 + 截图强制 URL），
**上线后报错依旧且引发密集报错，已整体 revert（a57b1f7）**。

V1.4.2 失败本身构成关键证据：该补丁已把 Web 并发从 40 压到 20（< 池容量 30），
若根因确为「Web 并发 > 池容量」，池不应再耗尽。**故 V1.4.2 的根因判断被证伪**，
本版本重新定位。

## 2. 根因

### 2.1 现象定位

`app/api/worker.py` 的 `run_once` 在**整个作业期间持有同一个 session**：

```python
session = self.session_factory()          # ①
job = claim_next_job(session)             # ② SELECT + commit
result = await self._execute(session, job)  # ③ 数百秒的 LLM 调用
finish_job(session, job, ...)             # ④
session.close()                           # ⑤ 此时才真正释放
```

②的 `commit()` 已结束事务并归还连接，但③开始时连接**被重新占用，且直到④才释放**。

### 2.2 触发机理：deferred 列的隐式重新取连接

`app/models/api_job.py:21` 的 `request_payload` 为 `deferred=True`（上一轮
「轮询不搬运大列」补丁引入）。`_execute` 中 `model_validate(job.request_payload)`
访问该延迟列时，SQLAlchemy 需发起一条 `SELECT request_payload FROM api_job`，
**这会重新开启事务并取走一条连接**；此后 session 一直挂着该连接直到下一次
commit（即④ `finish_job`）。中途 `set_progress` 的 commit 会短暂归还，但下一次
访问 job 属性又立刻占回。

### 2.3 实验验证

**实验一**（`scripts/diag_real_hold.py`）：用**真实 `ApiJobWorker` 代码路径**
（非模拟），替换 engine 为 SQLite QueuePool，注入阻塞式假 provider，
在"LLM 调用进行中"这一刻采样：

```
checkedout=0   基线（空闲）
checkedout=1   ★ LLM 调用进行中      ← 连接被握住
checkedout=0   作业结束后
```

**实验二**（`scripts/diag_deferred_cause.py`）：四格对照矩阵，隔离唯一变量：

| 场景 | claim 后 | LLM 期间 |
|---|---|---|
| deferred=True，访问 payload=True | 0 | **1 ← 连接被握住** |
| deferred=True，访问 payload=False | 0 | 0 |
| deferred=False，访问 payload=True | 0 | 0 |
| deferred=False，访问 payload=False | 0 | 0 |

**只有 `deferred=True` 且访问 payload 时连接被握住**，其余三种均为 0。
机理确证。

### 2.4 数量级：为何 V1.4.2 压到 20 仍然爆

实测每个 API Worker 在 LLM 期间稳态占用 **1 条**连接（`API_WORKER_CONCURRENCY=3`
→ 3 条）。单看 API Worker 不足以打满 30，但叠加后即超：

- `LLM_TIMEOUT_SECONDS=600`：单次调用最长 10 分钟，这些连接是**长时间死握**；
- 业务 Worker（`WORKER_CONCURRENCY=5`）的 pipeline 已有 `session.commit()`
  释放处理（`pipeline.py:43/99/139`），但 `worker.py` 的 `finish_task`/`advance`
  阶段仍持有；
- Web 侧每个在途同步请求经 `get_db()` 独占 1 条直到请求结束；
- 积压 1465 个 pending 作业使 worker 长期满负荷，上述占用是**稳态而非峰值**。

结论：**长期死握的连接抬高了基线水位**，剩余余量不足以吸收 Web 并发波动，
于是任何一侧（含 worker 自身的 `claim_next`）都可能撞到 pool_timeout。
这解释了为何单纯压 Web 并发无效——V1.4.2 治的不是这一半。

### 2.5 已排除项（沿用上一轮取证，未被本轮推翻）

- 连接泄漏/长事务：MySQL 侧观察到应用连接均为 `Sleep`、`active=0`；
- 进程反复重启：连接存活时长未归零；
- claim SQL 慢：命中索引，0.03s；
- CPU 阻塞事件循环：24.31MB `json.loads` 实测仅 0.059s。

## 3. 设计目标

1. **API Worker 在 LLM 调用期间不持有任何数据库连接**（持有时长从数百秒 → 毫秒级）；
2. 连接占用与 `API_WORKER_CONCURRENCY` **解耦**，使该并发数可安全上调以消化积压；
3. **零对外契约变更**——不动 API 请求/响应结构，不动 `.env` 必填项；
4. 可回归验证：先有能复现「连接被长期持有」的失败测试，再改代码。

> 明确不在本版本范围：截图 base64 → URL 的契约变更（V1.4.2 的另一半）。
> 该项与本根因无关（仅影响读 payload 那一下的耗时），且属破坏性变更，
> 须待对接方改造后单独发版。

## 4. 方案

### 4.1 核心改动：`run_once` 拆为三个短会话

```
会话1  claim_next_job + 读出 payload 为普通 dict  → 立即 close
       （无连接持有）await LLM 数百秒            ← 全程不碰 DB
会话2  set_progress（每次进度更新）              → 开→关
会话3  finish_job / fail_or_retry                → 立即 close
```

`_execute` 不再接收 ORM 对象与 session，改为接收**纯数据**（`job_id`、
`job_type`、`payload` dict），从根上杜绝任何延迟列触发隐式 SELECT。

### 4.2 改动清单

| 文件 | 改动 |
|---|---|
| `app/api/worker.py` | `run_once` 拆分为三段短会话；`_execute` 签名改为接纯数据（`job_id`/`job_type`/`payload`）；`progress_cb` 改为每次自开短会话 |
| `app/api/jobs.py` | 新增 `claim_next_job_detached`（认领并把 payload 取成普通 dict）、`set_progress_by_id` / `finish_job_by_id` / `fail_or_retry_by_id` 三个短会话入口、`_stripped_payload`（纯 dict 版截图剥离）；原有函数全部保留，业务路径与既有测试不受影响 |
| `tests/test_api_worker_session.py`（新增） | 6 项回归：3 项断言 LLM/识图期间会话无事务，3 项锁定截图剥离、失败重试保留 payload、进度落库 |

### 4.3 附带优化：终态不重读大列

短会话改造后，落终态需要一个新会话，若沿用 `_strip_screenshots`（就地修改
ORM 对象）会为剥离截图**重新 SELECT 数 MB 的 `request_payload`**（实测确认）。
由于 worker 内存中已持有 payload，故 `finish_job_by_id` / `fail_or_retry_by_id`
支持传入 `payload` 参数直接赋值已剥离版本，省去该次重读；不传时回退到原
就地剥离逻辑，保持向后兼容。

实测（`scripts/diag_worker_path.py`）：整个作业期间 `request_payload` 大列
只在认领时读 1 次（必需），LLM 期间 `checkedout=0`。

### 4.4 边界与权衡

- **`claim` 与 `finish` 之间作业无事务保护**：worker 崩溃会留下 running 孤儿作业。
  该风险**已有兜底**——`fail_stale_running_jobs`（30 分钟阈值）本就是为此设计，
  无需新增机制（`tests/test_api_job_stale.py` 已覆盖）。
- **`progress_cb` 变为同步短会话**：每条进度一次开关连接。按当前批次规模
  （评论 50-200 条/批、账号 20-50 个/批）频次可接受，且每次持有仅毫秒级。
- **`API_WORKER_CONCURRENCY` 上调留到验证后再做**：本版本只改会话生命周期，
  不改并发默认值，避免一次引入两个变量重蹈 V1.4.2 覆辙。

## 5. 验证结果

1. **失败测试先行**：新增 `tests/test_api_worker_session.py`，用真实
   `ApiJobWorker` 路径断言 LLM 调用发起时会话不持有事务。
   **改代码前 3 项断言全部失败**（实测 `[True] != [False]`），改后转绿——
   证明该测试确实锁住了这个 bug，而非空转。
2. **全量回归**：`234 passed`（基线 228 + 新增 6），无回归。
3. **真实路径实测**（`scripts/diag_real_hold.py`）：单作业连接峰值
   **1 → 0**；LLM 期间 `checkedout=0`。
4. **端到端复核**（`scripts/diag_worker_path.py`）：LLM 期间 `checkedout=0`，
   大列只在认领时读 1 次，终态截图剥离行为保持不变。

### 上线后观察项

- `QueuePool limit reached` 是否消失（关键指标）；
- 积压 pending 作业数是否开始下降；
- running 作业是否出现异常增多（若有，说明短会话间隙的孤儿作业比预期多，
  由 stale reaper 兜底，但需复核阈值）。

## 6. 遗留事项（不在本版本）

- **P1** 验证生效后上调 `API_WORKER_CONCURRENCY` 以消化积压（本版本后该值
  不再线性吃连接，可安全上调）；
- **P2** `/api/v1/jobs/{job_id}` 增加 HEAD 支持（当前返回 405；其后续 GET 多为
  401，说明这些轮询方持有无效 API Key，值得联系对接方核对）；
- **P3** 清理 206 条残留 base64 与 6407MB 的 `api_job` 表；
- **P4** 截图强制 URL 契约变更（须对接方先改造，不可单方面上线）；
- **约束**：MySQL `Max_used_connections=152` vs `max_connections=151` 已打满，
  **任何调大 `DB_POOL_SIZE` 的动作前必须先提升 MySQL `max_connections`**。
