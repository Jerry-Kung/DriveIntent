# V1.10.1 补丁：管理页卡顿定位与修复

> 版本：V1.10.1 | 日期：2026-09-10 | 类型：补丁（性能修复，对外契约不变）

## 1. 现象

内部管理页 `http://<IP>:8000` 明显卡顿：

| 页面 | 实测延迟 |
|---|---|
| `/leads`（线索列表）打开/刷新 | 约 5s |
| `/leads?grade=H`（等级筛选） | 约 140s（几乎不可用） |
| `/audit`（审计统计）打开/刷新 | 10s+ |

用户侧感知与实测一致。本文记录定位过程、根因与修复，并给出验收数据。

## 2. 定位过程与实测数据

全部数据来自生产库（MySQL 8.2.0，远程实例）实测，非估算。

### 2.1 库内现状

| 表 | 行数 | 数据 | 索引 |
|---|---|---|---|
| `api_job` | 88,957 | 3,321 MB | 10 MB |
| `llm_call_log` | 1,227,136 | 10,553 MB | 105 MB |

服务端参数：`innodb_buffer_pool_size=128 MB`、`innodb_io_capacity=200`。
数据量 14 GB 远超 128 MB 缓冲池，绝大多数读取走磁盘。

### 2.2 根因一：模型声明的索引在生产库不存在

对比模型定义与库内 `information_schema.statistics`：

| 表 | 模型声明 | 库内实际 |
|---|---|---|
| `api_job` | `ix_api_job_finished`、`ix_api_job_status_order` | **仅** `ix_api_job_status_order` |
| `llm_call_log` | `ix_llm_call_created`、`ix_llm_call_job` | **仅** `ix_llm_call_job` |

成因：`init_db()` 走 SQLAlchemy `create_all`，它**只创建缺失的表，不会给已存在的表补建索引**。这两个索引是在表已存在之后才加进模型的，因此从未落库。而 `tests/test_audit_stats.py` 断言这两个索引存在却一路通过——测试用的是全新建库，`create_all` 会把索引一并建出。测试与生产在建库路径上的这一差异是问题长期潜伏的原因。

后果（实测）：

| 查询 | 耗时 | 执行计划 |
|---|---|---|
| 审计页 `today_summary` | 5.26s | `type=ALL`（全表扫 67 万行） |
| 审计页 `llm_stats` | 4.60s | `type=ALL` + `Using temporary` |
| `_base_query.count()` | 1.24s | `range` + `Using index condition` |
| `leads` 首页 | 8.31s | `Using filesort`（缺 `finished_at` 索引） |

### 2.3 根因二：线索列表在查询期展开 `result` 大列

`lead_results.query_lead_results` 的首页路径需要 `JSON_LENGTH(result,'$.results')` 才能算分页游标，而取长度必须读取 `result` 列本身。实测：

- `result` 全量 **346 MB**，平均 **50 KB/作业**（单作业含约 50 个账号，每次分析文本数 KB）；
- 首页要搬运 **7,248** 个作业的完整 JSON（实测 `ids + json_length` 5.55s）；
- 等级筛选走 `_all_rows`，把 346 MB 全部反序列化成 Python 字典再过滤：**139.13s**。

即：为了渲染 20 行，系统搬运并解析了 346 MB。

## 3. 修复

### 3.1 补索引（`scripts/add_perf_indexes.py`，已执行）

```sql
ALTER TABLE api_job      ADD INDEX ix_api_job_finished (finished_at);
ALTER TABLE api_job      ADD INDEX ix_api_job_leads (job_type, status, finished_at, id);
ALTER TABLE llm_call_log ADD INDEX ix_llm_call_created (created_at);
```

幂等脚本，可在服务运行中执行（InnoDB 在线 DDL）。实测建索引耗时分别为 1.6s / 1.0s / 4.8s。`ix_api_job_leads` 覆盖线索列表的筛选与排序，消除 filesort。

### 3.2 线索汇总表 `lead_record`（新增）

把列表所需字段在**作业终态**时物化为一账号一行：

- 写入时机：`finish_job` / `finish_job_by_id` 落终态时**同一事务**写入；终态失败（含停滞兜底）清掉该作业旧行；
- 主键 `(job_id, idx)`：重跑/重试天然幂等，不产生重复行；
- 索引按列表排序方向声明（`finished_at DESC, job_id DESC, idx ASC`，MySQL 8 降序索引），翻页免排序；
- 排序口径与旧实现逐字对齐：同一 `finished_at` 的作业按作业 id 倒序、单作业内按账号下标升序，故**任意页的切分点与旧版一致**，前端分页体验无变化；
- `analysis` 等大文本仍存（CSV 导出需要），但列表查询不再触碰 `api_job.result`。

历史数据由 `scripts/backfill_lead_records.py` 回填（幂等 upsert、可续跑、`--dry-run`），与线上服务互不阻塞。

### 3.3 切换判据：就绪标记（而非"表非空"）

回填脚本按 `finished_at` **升序**写入，而列表按时间**倒序**展示。若以"汇总表有数据"作为切换判据，回填中途失败时列表会**静默地**只显示最旧的那批作业——恰恰是最该看到的最新线索不见了，且用户无法察觉。

因此切换判据是**就绪标记文件** `data/lead_record_ready`：

| 场景 | 标记 | 行为 |
|---|---|---|
| 回填未开始 / 中途失败 | 无 | 走 JSON 回退路径（慢但完整） |
| 回填自检通过 | 脚本写入 | 走汇总表快路径 |
| 全新部署（无历史作业） | 服务启动时自动写入 | 走汇总表快路径，无需跑回填 |
| 标记误删但表已完整 | 无 | 走回退路径；重跑回填脚本（幂等）即恢复标记 |

标记与截图暂存区同在 `./data` 挂载点下，docker 与裸机部署均可共享；服务启动时 `ensure_marker_for_fresh_db` 只在**确无历史精筛作业**时才自动标记，不会为已有历史作业的库放行。

### 3.4 回退路径（不破坏可用性）

汇总表未就绪时（未回填的旧库、回填中途、标记缺失），服务自动回退原来的 JSON 展开实现，结果口径一致，仅慢。这样迁移期与新建环境都不会出现"列表空白"或"列表不全"。

### 3.5 未做的改动及原因

- **未改 `innodb_buffer_pool_size`**：属测试库运维操作、影响同实例其他库，待用户授权后另行执行；
- **未加日志保留策略**：`llm_call_log` 已占 10.5 GB（1,227,136 行，约 9 KB/行），建议评估清理窗口，但涉及数据删除决策，交用户决定；
- **未改审计页 SQL 形状**：补索引后审计两条聚合已从全表扫降为范围扫，改形状收益有限，保持最小改动。

## 6. 遗留事项

1. **回填未执行**：写库操作被本地权限策略拦截，需在生产/测试环境执行 `python scripts/backfill_lead_records.py`（实测全量约 3 分钟，脚本自检通过后自动写就绪标记）。在此之前列表页走回退路径，等级筛选仍慢；
2. **列表等级筛选的回退路径未优化**：就绪前 `grade` 筛选仍是 140s 量级的全量展开；这是有意为之——一旦回填完成，该路径不再被触发；
3. **`innodb_buffer_pool_size` 与 `llm_call_log` 保留策略**：待用户决策；
4. **测试环境验证**：需在测试环境复核两项实际观测——`/leads` 与 `/audit` 的响应时间、以及回填后列表总数与筛选结果是否与回填前一致（可用部署文档 §10.1 的核对 SQL 交叉验证）。当前已完成的验证范围为：真库上的索引效果实测、汇总表方案在同构影子表上的实测、以及 460 项单元/接口测试。
