# V1.6.3 设计：复核改级后同步修订对外叙述

> 版本：V1.6.3 | 日期：2026-08-12

## 1. 背景与问题

V1.6.2 在定级节点之后新增了独立复核节点（`user_lead_review`），它以销售经理视角
复核初步评级，输出 `review_action`（confirmed / upgraded / downgraded）与
`reviewed_grade`。pipeline 在复核非 confirmed 时覆写最终等级：

```python
# app/workflow/pipeline.py（V1.6.2）
if review.review_action != "confirmed":
    out.lead_grade = review.reviewed_grade
```

**问题**：复核节点只调整 HABC 等级，不触碰任何叙述字段。而 `analysis_text`、
`lead_summary` 是定级节点针对**初步评级**写就的。一旦复核改级，就产生自相矛盾的
对外输出——最终等级为 H，但 `analysis` 全文在论证该用户为何是 A 级。

**影响面**：`analysis_text` 经 `app/api/mapping.py:91,102` 原样透传为
`ProfileResult.analysis`；`lead_summary` 经 `app/services/leads.py:19` 落入
`Lead.summary`。两者都直接呈现给销售人员，矛盾文本会削弱线索情报的可信度，
与 V1.6.1 确立的"对外文本面向销售人员可读"这条主线相悖。

**发生条件**：仅当 `review_action != "confirmed"` 时发生；升级与降级同样会矛盾。

## 2. 范围决策（已与用户确认）

1. **修订载体：复核节点**。由复核节点在改级时一并输出修订后的叙述文本，
   而非新增第三个节点或让定级节点跑第二轮。
2. **修订粒度：只改与等级绑定的部分**，不整段重写。`analysis_text` 五段中
   仅第五段"总体评价"与 HABC 绑定，前四段是事实陈述（评论行为、购车阶段、
   车型匹配、主页画像），与等级无关。复核节点的信息量少于定级节点，
   让它覆盖事实性内容属净损失。
3. **字段范围：`analysis_text` 第五段 + `lead_summary`**，共两处。
   明确排除 `purchase_stage`——它是从评论读出的事实判断（用户走到哪一步），
   不是等级的函数；一个处于"初步了解"阶段的用户完全可以因持续深度关注被判 H，
   两者不矛盾，强行联动会制造新的失真。同样排除
   `recommended_entry_point`、`verification_questions`、`profile_summary`、
   `profile_tags`、`core_needs`、`main_concerns`、`target_*`。
4. **替换机制：代码切分，非模型自行照抄**。要求模型"前四段原样照抄"是它做不
   可靠的事——实测会改写、压缩、丢细节，等于变相退化为整段重写。只有代码切分
   能兑现"前四段零失真"这个承诺。
5. **对外契约不变**：新增字段均为内部审计字段，`ProfileResult.analysis` 等
   对外字段的类型与语义不动。
6. **历史数据不回填**：与项目惯例一致，已落库旧结果保持原样。

## 3. 方案

### 3.1 数据流

```
过滤节点 ──命中──> 合成 C 级结果（跳过定级与复核，不变）
   │未命中
   ▼
定级节点 v1.6.3 ──> 初步 lead_grade + analysis_text（五段带标题）+ lead_summary
   │
   ▼
复核节点 v1.6.3 ──> review_action / reviewed_grade / review_reason
   │                + revised_conclusion（仅改级时）
   │                + revised_lead_summary（仅改级时）
   ▼
pipeline 合并 ──> confirmed：只写审计字段，文本不动
                改级：替换 analysis 第五段 + 覆盖 lead_summary，再改 lead_grade
```

### 3.2 定级 Prompt：`user_lead_analysis_v1.6.3.txt`（由 v1.6.2 复制修改）

三阶段流水线、独立标签判定、结构化审计字段输出要求、V1.6.1 可读性禁令
全部一字不动。**唯一实质改动**是给 `analysis_text` 增加格式约束：五段各以
固定中文标题起首，标题独占一行，标题文字必须逐字一致（供下游锚点定位）：

```
一、评论行为与用户身份
二、购车阶段评估
三、目标车型与我方车型匹配度
四、主页画像与调整结论
五、总体评价
```

字数区间（400-700 字）与各段内容要求保持不变。带标题对销售人员本身即更易读，
与 V1.6.1 可读性主线同向。

### 3.3 复核 Prompt：`user_lead_review_v1.6.3.txt`（由 v1.6.2 复制修改）

既有复核逻辑（独立形成第一判断、比对初步评级、单次不得跨越一级、C 为下限）
不变。新增一节输出要求：

当且仅当 `review_action != "confirmed"` 时，额外输出

- `revised_conclusion`：新的"总体评价"**正文**，80-200 字，**不含段标题**
  （标题由代码补齐，避免重复）。要求承接前四段既有事实、只改写价值结论，
  并说明改级依据。
- `revised_lead_summary`：新的 1-2 句速读结论，与 `lead_summary` 原有要求一致
  （说明用户目标车型与我方车型的关系）。

`review_action == "confirmed"` 时两字段输出 `null`。两字段同受 V1.6.1
可读性禁令约束：不得出现英文字段名、枚举值或布尔字面量。

### 3.4 Schema 变更（`app/schemas/skills.py`）

`UserLeadReviewResult` 新增两个可选字段：

```python
revised_conclusion: str | None = None    # 新"总体评价"正文，不含标题
revised_lead_summary: str | None = None  # 新速读结论
```

`UserLeadResult` 新增一个审计字段（内部用，不进对外契约，与既有
`profile_adjustment` / `match_adjustment` 同风格）：

```python
analysis_revision: str = "none"  # none | replaced | appended
```

该字段的作用是**可观测性**：直接暴露锚点命中率。若生产上 `appended` 占比偏高，
说明定级模型未稳定按格式输出标题，格式约束需加强；无此字段则只能靠人工翻查
结果才能发现无声退化。

审计链条完整形态：

```
baseline_grade →(match_adjustment)→ 中间等级
               →(profile_adjustment)→ pre_review_grade
               →(review_action)→ lead_grade
               →(analysis_revision)→ 对外叙述文本
```

### 3.5 pipeline 拼接与兜底（`app/workflow/pipeline.py`）

新增模块级常量与私有函数：

```python
CONCLUSION_ANCHOR = "五、总体评价"
```

**替换规则**：对 `analysis_text` 取锚点的**最后一次**出现（`rfind`）。总体评价是
末段，用末次匹配可避开前文对该标题的引用。保留锚点之前的全部内容逐字不变，
拼上锚点 + 换行 + 新正文。若 `revised_conclusion` 自带标题则先剥除，防止重复。

**三级兜底**，逐级降级、均不抛错：

| 情形 | 行为 | `analysis_revision` |
|---|---|---|
| 锚点命中 | 替换第五段，前四段逐字保留 | `replaced` |
| 锚点缺失 | 文末追加 `五、总体评价（复核修订）` + 新正文，原文完整保留 | `appended` |
| `revised_conclusion` 为空 | 文本完全不动；等级仍按复核结果改 | `none` |

`revised_lead_summary` 为空时 `lead_summary` 保持原值。

**触发条件**：修订与等级覆写由同一个判据驱动——`review_action != "confirmed"`，
两者严格同进同退。`confirmed` 时不进入修订分支，`analysis_revision` 保持默认
`"none"`。若模型输出 `review_action != "confirmed"` 但 `reviewed_grade` 与初步
等级相同（模型自相矛盾），仍按判据走修订分支：此时文本被改写为复核措辞而等级
未变，不产生矛盾，且 `analysis_revision` 会留下痕迹供排查。

**原子性约束（关键）**：先把新等级与新文本全部计算完毕，最后一次性赋值。
绝不允许出现"等级已改、文本替换中途失败"的中间态——那正是本版要消灭的矛盾。
替换为纯字符串运算、实际不会抛错，但赋值顺序仍按此约束写死。

**fail-open 语义不变**：外层 `try/except` 保持原样，复核调用本身失败时，
等级与文本双双保持初步结果。被过滤用户仍完全跳过复核。

### 3.6 代码配套（版本号与遗留清理）

| 文件 | 改动 |
|---|---|
| `app/skills/configs/user_lead_analysis.yaml` | `version: "1.6.3"`、`prompt_file: user_lead_analysis_v1.6.3.txt`、`prompt_version: "v1.6.3"`；并将 V1.6.2 临时英文期遗留的英文 `description` 改回中文（`086466e` 只改了 Prompt 未改 YAML） |
| `app/skills/configs/user_lead_review.yaml` | 同上升 `"1.6.3"` / `user_lead_review_v1.6.3.txt` / `"v1.6.3"`；`description` 补充叙述修订职责 |
| `app/workflow/pipeline.py` | `SKILL_VERSIONS` 两项 → `"1.6.3"`；新增锚点常量与拼接逻辑 |

**影响**：`SKILL_VERSIONS` 升版使 V0 流水线路径旧版本定级结果失效并触发重分析
（与历次升版行为一致）；API 路径无状态，不受影响。

### 3.7 明确不做

- 不修订 `purchase_stage` 及其他事实性抽取字段（见 2.3）；
- 不整段重写 `analysis_text`；
- 不新增第三个 LLM 节点，不让定级节点跑第二轮；
- 不动过滤 Prompt、Agent1 初筛 Prompt；
- 不回填/清洗历史落库数据；
- 对外 API 契约、DB schema、映射逻辑均不动；
- 旧 Prompt 文件（v1.6.2）保留不动、不再被引用（VERSIONING.md 规则）。

## 4. 测试

现状缺口：`tests/test_user_analysis.py` 只给 MockProvider 排入「过滤 + 定级」
两个响应，复核调用因队列耗尽抛错、被 fail-open 吞掉——**复核路径目前无测试覆盖**。
本版补齐。

新增 `tests/test_user_review.py`：

1. 锚点命中 → `analysis_revision == "replaced"`，且**前四段逐字节相等**
   （C 方案的核心承诺，必须断言）；
2. 锚点缺失 → `"appended"`，原文完整保留；
3. `confirmed` → `analysis_text` 与 `lead_summary` 均一字未改，
   `analysis_revision == "none"`；
4. `downgraded` → 同样触发修订（升降级对称性）；
5. `revised_conclusion` 为空 → `"none"`，文本不动，但等级仍改；
6. `revised_conclusion` 自带标题 → 输出中不出现重复标题；
7. 复核调用抛异常 → 等级与文本**同时**保持初步值（fail-open + 原子性）。

更新现有断言：

8. `tests/test_agent2.py`、`tests/test_user_analysis.py` 的
   `prompt_file` / `prompt_version` / `SKILL_VERSIONS` 升 v1.6.3；
9. 给 `tests/test_user_analysis.py` 现有用例补上复核响应，使复核路径真正被走到，
   而非靠异常吞掉；
10. 新增 Prompt 内容断言：两个新 Prompt 文件存在、占位符齐全
    （定级：`$user_evidence_json` / `$grading_standard` / `$our_models_summary`；
    复核：另加 `$preliminary_result_json`）；定级 Prompt 含五个段标题字面量；
    复核 Prompt 含 `revised_conclusion` / `revised_lead_summary` 字段说明。

**验收（用户侧）**：真实 LLM 联调观察——改级样本的 `analysis` 第五段是否与最终
等级一致、前四段是否保持原貌；统计 `analysis_revision` 分布确认锚点命中率。
列为发版观察点。
