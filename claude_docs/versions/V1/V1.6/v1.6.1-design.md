# V1.6.1 设计：analysis 字段可读性修复——对外文本禁用内部审计字段

> 版本：V1.6.1 | 日期：2026-08-11

## 1. 背景与问题

Agent2 用户精筛&定级的对外输出 `analysis` 字段中混入了大量内部审计字段的明文复述，
外部用户（销售/运营人员）无法理解。真实案例（前端页面所见）：

> is_car_owner判定为true，has_purchase_intent判定为true（综合分析），
> 综合判定为similar档（意向车型匹配评估），merge_boost为none（终判调整）。

**根因**：对外 `analysis` 就是 LLM 输出的 `analysis_text` 原样透传
（`app/api/mapping.py` → `ProfileResult.analysis`）。而定级 Prompt
（`user_lead_analysis_v1.6.txt`）对 `analysis_text` 的指令是
"需说明基线、匹配档位与各段调整（含合并增强的触发或未触发情况）"——
直接点名内部机制字段，诱导 LLM 在分析文本中复述 `is_car_owner`、`merge_boost`、
`similar` 等英文字段名与枚举值。

**关键事实**：内部审计信息已由结构化字段完整承载（`baseline_grade`、
`model_match_level`、`match_adjustment/match_reason`、
`profile_adjustment/adjustment_reason`、`merge_boost/merge_boost_reason` 等，
不进对外契约但已落库/留痕），`analysis_text` 并非审计信息的载体，
两者职责本应分离。

## 2. 范围决策（已与用户确认）

1. **修复范围：定级 + 过滤两个 Prompt**。对外 `analysis` 共三个来源：
   ①定级 Prompt（主现场）；②V1.6 无效用户过滤 Prompt（被过滤用户的
   `analysis_text` 经 `build_filtered_lead_result` 同样对外，含同类风险）；
   ③Agent1 初筛 `reason`（透传为初筛结果 `analysis`）。本版本覆盖①②；
   ③风险较低（一句话理由），暂不动。
2. **不新增 `inner_analysis` 字段**：审计叙述由既有结构化字段承载，
   再加自由文本字段属重复建设，且徒增 tokens 成本。零契约变更。
3. **analysis 形态：保留六段结构 + 业务化表达**：信息量不减，
   仅表达方式改为面向销售人员的自然中文。
4. **历史数据不回填**：已落库旧结果保持原样（与项目"历史数据回退口径勿改"
   惯例一致）；对接方重新提交分析即得新格式。

## 3. 方案（方案 A：纯 Prompt 约束）

仅升版 Prompt 与配套版本号，零代码逻辑变更、零契约变更。
若联调后仍观察到泄漏，再考虑追加代码层兜底（本版本不做）。

### 3.1 定级 Prompt：`user_lead_analysis_v1.6.1.txt`（由 v1.6 复制修改）

四段流水线机制、结构化审计字段输出要求一字不动，改动集中三处：

1. **重写 `analysis_text` 字段说明**：保留六段，段名与要求业务化——
   "评论行为与用户身份 / 购车阶段 / 意向车型与我方在售车型匹配情况 /
   主页画像 / 评级调整说明 / 综合评价"。仍要求说明评级理由与各环节
   调整结论（含合并增强触发与否、两个独立标签的判定依据），但明确
   "以不了解本系统的销售人员为读者，用自然中文叙述"；删除
   "说明基线、匹配档位与各段调整"等点名内部字段的措辞。
2. **新增全局可读性禁令**（"要求"列表追加一条）：`lead_summary`、
   `profile_summary`、`analysis_text`、`recommended_entry_point`、
   `profile_tags` 等所有面向人的文本字段中，不得出现任何英文字段名、
   枚举值或布尔字面量（如 `is_car_owner`、`merge_boost`、`similar`、
   `true/false`），不得复述 JSON 输出结构的字段名；相关结论一律改用
   中文业务表达（如"判定该用户为车主""意向车型与我方车型同类且价位
   接近，评级维持不变"）。品牌/车型名等业务专名不受限。
3. **附正/反示例各一**：反例取自真实泄漏文本，正例为业务化改写。

### 3.2 过滤 Prompt：`user_lead_filter_v1.6.1.txt`（由 v1.6 复制修改）

- `analysis_text`（过滤判定说明）、`profile_summary`、`profile_tags`
  加同样的可读性禁令与业务化表达要求；
- `filter_reason` 存在对外兜底路径（`analysis_text` 为空时透传，
  `app/skills/user_filter.py`），同样要求业务化中文表述；
  其审计定位不变，仍须引用具体评论/画像证据。

### 3.3 代码配套（仅版本号）

| 文件 | 改动 |
|---|---|
| `app/skills/configs/user_lead_analysis.yaml` | `version: "1.6.1"`、`prompt_file: user_lead_analysis_v1.6.1.txt`、`prompt_version: "v1.6.1"` |
| `app/skills/configs/user_lead_filter.yaml` | 同上升 `"1.6.1"` / `user_lead_filter_v1.6.1.txt` / `"v1.6.1"` |
| `app/workflow/pipeline.py` | `SKILL_VERSIONS[USER_ANALYSIS_SKILL]` → `"1.6.1"`（配置一致性断言要求同步） |

**影响**：`SKILL_VERSIONS` 升版使 V0 流水线路径旧版本定级结果失效并触发
重分析（与历次升版行为一致）；API 路径无状态，不受影响。此为既有升版
机制，不属于第 2 节所述"历史数据回填"。

### 3.4 明确不做

- 不新增 `inner_analysis` 或其他任何字段；对外 API 契约、DB schema、
  映射逻辑均不动；
- 不回填/清洗历史落库数据；
- 不动 Agent1 初筛 Prompt（`comment_lead_screening_v3.txt`）；
- 不加代码层正则检测/清洗兜底（留作联调后观察项）；
- 旧 Prompt 文件（v1.6）保留不动、不再被引用（VERSIONING.md 规则）。

## 4. 测试

1. **更新现有断言**：`tests/test_agent2.py`（prompt_file/prompt_version/
   SKILL_VERSIONS）、`tests/test_user_filter.py`（prompt_file/prompt_version）
   升 v1.6.1；
2. **新增 Prompt 内容断言**：两个新 Prompt 文件存在、占位符齐全
   （定级：`$user_evidence_json`/`$grading_standard`/`$our_models_summary`；
   过滤：`$user_evidence_json`）；含可读性禁令关键句；定级 Prompt 不再
   含旧诱导措辞（如"匹配档位与各段调整"）；
3. **验收（用户侧）**：真实 LLM 联调观察对外 `analysis` 是否仍出现
   英文字段名/枚举值，列为发版观察点。
