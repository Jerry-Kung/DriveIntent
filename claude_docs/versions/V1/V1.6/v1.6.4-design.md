# V1.6.4 设计：analysis 润色节点 + 复核接入 API 路径

> 版本：V1.6.4 | 日期：2026-08-13

## 1. 背景与问题

测试环境（对外 API 路径）运行结果显示，Agent2 精筛输出的 `analysis` 字段仍存在
两类质量问题：

1. **遵从性问题**：`analysis_text` 中出现英文字段名、枚举值或布尔字面量
   （如 `is_car_owner`、`profile_adjustment`、`similar`、`true`、`false`）。
   V1.6.1 已在定级 Prompt 中写明可读性禁令，但 LLM 经常不遵守；
2. **一致性问题**：复核节点调整定级后，重写的 analysis 部分与未重写的其他
   内容细节对不上（叙述论证 B 级理由，最终定级却是 A）。

**探索发现的关键事实**：V1.6.2 复核节点与 V1.6.3 叙述修订**只接在 V0 流水线
路径**（`app/workflow/pipeline.py`），对外 API 路径（`app/api/agent2.py`）
目前是「过滤 → 定级」即结束，连复核节点都没有。测试环境走的正是 API 路径——
这解释了 V1.6.3 发版后测试环境仍能看到改级矛盾。全仓 `USER_REVIEW_SKILL`
仅 `pipeline.py` 一处引用可为佐证。

## 2. 范围决策（已与用户确认）

1. **接入路径：先把复核接入 API 路径，再在复核后统一接润色节点**，
   两条路径（V0 流水线 / 对外 API）节点序列完全对齐；
2. **润色触发条件：所有走完定级+复核的结果都润色**（含 confirmed 未改级的）。
   英文字段泄漏与是否改级无关，任何结果都可能出现；被前置过滤命中的账号
   （合成 C 级、analysis 为过滤理由短文本，不经过定级与复核）跳过润色；
3. **润色范围：全部对外叙述字段**——`analysis_text` + `lead_summary` +
   `profile_summary`，一次调用同时润色；
4. **失败策略：fail-open**。润色调用失败保留润色前文本照常出结果，
   记审计字段 + warning 日志，与过滤/复核节点惯例一致；
5. **权限边界：只改文本不改级**。润色节点无权改 `lead_grade` 及任何结构化
   字段；发现叙述与最终定级矛盾时，以最终定级为准重写叙述；
6. **方案选型：独立润色 Skill + 共享模块（方案 A）**。否决了「把全量润色
   合并进复核节点」（V1.6.3 已实证模型「原样照抄」不可靠，且 confirmed
   场景也要重写全文会使单次任务复杂度上升、遵从性更差）与「代码正则清洗」
   （治不了语义矛盾）。

## 3. 方案

### 3.1 数据流

两条路径统一为同一节点序列：

```
过滤节点 ──命中──> 合成 C 级结果（不变，不润色）
   │未命中
   ▼
定级节点（prompt 不变，v1.6.3）
   ▼
复核节点（prompt 不变，v1.6.3）──> 改级时 C-1 锚点修订第五段（V1.6.3 机制保留）
   ▼
润色节点（新增，v1.6.4）──> 重写 analysis_text / lead_summary / profile_summary
   ▼
落库（V0 路径）/ 映射对外结果（API 路径）
```

V1.6.3 的锚点修订机制**保留不删**：它是润色节点 fail-open 时的兜底防线——
润色失败时，改级样本至少第五段已被代码修正过。两层防御叠加。

### 3.2 复核逻辑抽出为共享模块（`app/skills/user_review.py`，新增）

把现在内联在 `pipeline.py` 的复核调用、`CONCLUSION_ANCHOR`、
`_revise_analysis`、审计字段赋值整体迁入，暴露：

```python
async def apply_review(executor, evidence_json: str,
                       our_models_summary: str, out: UserLeadResult) -> None
```

就地修改 `out`（写 `pre_review_grade` / `review_action` / `review_reason` /
`analysis_revision`，改级时替换第五段、覆盖 `lead_summary`、覆写
`lead_grade`）。`pipeline.py` 与 `agent2.py` 都调用它——API 路径由此首次获得
复核能力。

顺手修复：现有裸 `except Exception: pass`（复核静默失效无从察觉）改为与
`user_filter.py` 一致的「精确捕获 `SkillExecutionError` + warning 日志」，
fail-open 语义不变。

### 3.3 润色共享模块（`app/skills/analysis_polish.py`，新增）

```python
async def apply_polish(executor, out: UserLeadResult) -> None
```

就地修改 `out` 的三个叙述字段与 `analysis_polish` 审计字段，两条路径复用。

**输入契约**（刻意不给用户证据包）：最终 `lead_grade` + `review_action` /
`review_reason`（为润色第五段提供改级背景，可为空）+ 三个待润色文本。
不给证据包的理由：润色是纯文本改写任务，给证据包会诱导模型引入新事实、
且白白增加 token；信息量少反而是遵从性的保障。

### 3.4 Schema 变更（`app/schemas/skills.py`）

新增润色节点输出模型：

```python
class AnalysisPolishResult(BaseModel):
    polished_analysis_text: str = ""
    polished_lead_summary: str = ""
    polished_profile_summary: str = ""
    confidence: float = 0.0
```

`UserLeadResult` 新增一个审计字段（内部用，不进对外契约，风格同
`analysis_revision`）：

```python
analysis_polish: str = "none"  # none | polished | failed
```

- `none`：未走润色（被过滤账号）；
- `polished`：润色已应用（含 summary 单字段为空、部分应用的情形）；
- `failed`：调用失败或输出非法，保留原文。

作用是**可观测性**：测试环境可统计润色实际生效率，防止 V1.6.2 那种
「fail-open 吞掉异常、节点长期空转无人察觉」的无声退化重演。

审计链条完整形态：

```
baseline_grade →(match_adjustment)→ 中间等级
               →(profile_adjustment)→ pre_review_grade
               →(review_action)→ lead_grade
               →(analysis_revision)→ 锚点修订后叙述
               →(analysis_polish)→ 对外叙述文本
```

### 3.5 润色 Prompt（`user_analysis_polish_v1.6.4.txt`，新增）

角色设定为「面向汽车销售团队的报告编辑」。核心指令：

1. **保持五段结构与段标题逐字不变**（锚点约束延续）；各段字数与原文相当，
   事实细节（车型名、评论内容引用、时间等）逐一保留，
   **严禁新增原文没有的事实**；
2. **清除英文审计字段泄漏**：出现英文字段名、枚举值、布尔字面量一律改写为
   自然中文业务表述（正/反例沿用定级 Prompt 可读性条款的示例）；
3. **消除内部矛盾**：全文的价值判断、跟进优先级必须与传入的最终定级一致；
   若某段落论证的等级与最终定级不符，以最终定级为准改写该论证
   （可参考传入的复核理由）；
4. 顺畅衔接、消除歧义与重复；`lead_summary` / `profile_summary` 同受
   上述约束；
5. 输出严格 JSON（三个 polished 字段 + confidence）。

占位符：`$lead_grade`、`$review_action`、`$review_reason`、
`$analysis_text`、`$lead_summary`、`$profile_summary`。

注意：Prompt 正文经 `string.Template.substitute` 渲染，正文中不得出现
裸 `$`（会抛错）。

### 3.6 错误处理与语义校验

`apply_polish` 的 fail-open 分层（保留原文、记 `failed`、warning 日志，
绝不阻断主流程）：

| 情形 | 行为 | `analysis_polish` |
|---|---|---|
| `SkillExecutionError`（LLM/解析/校验失败） | 三个字段全部保留原文 | `failed` |
| `polished_analysis_text` 为空 | 三个字段全部保留原文（整体输出不可信） | `failed` |
| `polished_analysis_text` 缺失任一五段标题 | 三个字段全部保留原文（结构被破坏，宁可不用） | `failed` |
| `polished_lead_summary` / `polished_profile_summary` 单独为空 | 该字段保留原值，其余照常应用 | `polished` |
| 全部合法 | 三个字段一并替换 | `polished` |

赋值遵循 V1.6.3 的原子性约束：校验全部通过后一次性赋值，不允许
「部分字段已换、部分字段校验失败」的中间态。

### 3.7 代码配套（版本号与接线）

| 文件 | 改动 |
|---|---|
| `app/skills/configs/user_analysis_polish.yaml` | 新增，`version: "1.6.4"`、`prompt_file: user_analysis_polish_v1.6.4.txt`、`prompt_version: "v1.6.4"` |
| `app/skills/prompts/user_analysis_polish_v1.6.4.txt` | 新增 |
| `app/skills/user_review.py` | 新增（从 `pipeline.py` 迁移复核逻辑 + 日志修复） |
| `app/skills/analysis_polish.py` | 新增 |
| `app/workflow/pipeline.py` | 复核段改为调用 `apply_review`；其后接 `apply_polish`；`SKILL_VERSIONS[USER_ANALYSIS_SKILL]` → `"1.6.4"` |
| `app/api/agent2.py` | `analyze_account` 之后接 `apply_review` + `apply_polish` |
| `app/skills/configs/user_lead_analysis.yaml` | 仅 `version` 升 `"1.6.4"`（维持「YAML version == `SKILL_VERSIONS`」项目不变式，`tests/test_agent2.py` 有断言守护）；`prompt_file` / `prompt_version` 维持 v1.6.3 |
| 定级/复核 Prompt 文件与复核 YAML | **不动**（内容无变化，维持 v1.6.3；VERSIONING 规则：只在变更版本重命名） |

**影响**：`SKILL_VERSIONS` 升版使 V0 流水线路径旧版本定级结果失效并触发
重分析（与历次升版行为一致）；API 路径无状态，无此影响。

每账号 LLM 调用次数：过滤+定级+复核+润色 = 4 次（识图另计），
较 V1.6.3 的 API 路径（过滤+定级 2 次）翻倍——其中复核是已确认的路径补齐，
润色是本版新增。

### 3.8 明确不做

- 不动定级 Prompt、复核 Prompt、过滤 Prompt、Agent1 初筛 Prompt；
- 不删 V1.6.3 锚点修订机制；
- 被过滤账号不润色；
- 不回填/清洗历史落库数据；
- 对外 API 契约（`ProfileResult`）、DB schema、映射逻辑均不动；
- 不给润色节点独立的深度思考/模型配置（沿用全局设置与既有 YAML 机制）。

## 4. 测试

MockProvider 为 FIFO 队列，测试走完整真实链路。V1.6.2 教训（队列少排一个
响应，节点调用被 fail-open 吞掉，路径长期零覆盖却全绿）是本节的核心防线：
**每个集成用例必须断言审计字段证明节点真实走到**。

1. 新增 `tests/test_analysis_polish.py`：
   - 正常润色 → 三字段替换，`analysis_polish == "polished"`；
   - 输出为空 / 缺任一段标题 → 三字段保留原文，`"failed"`；
   - 执行异常 → fail-open，三字段保留原文，`"failed"`；
   - summary 单字段为空 → 部分应用，`"polished"`；
2. `tests/test_agent2.py`：API 路径集成用例 MockProvider 队列补齐为
   4 个响应（过滤+定级+复核+润色）；断言 `review_action` 与
   `analysis_polish` 审计字段；被过滤账号断言 `analysis_polish == "none"`
   且无多余 LLM 调用；对外 `analysis` 字段为润色后文本；
3. `tests/test_user_analysis.py` / `tests/test_user_review.py` /
   `tests/test_e2e.py` 等既有用例：补润色响应进队列；
   `SKILL_VERSIONS` 断言升 `"1.6.4"`；
4. 新增 Prompt 内容断言：`user_analysis_polish_v1.6.4.txt` 存在、
   占位符齐全（3.5 节六个）、含五段标题字面量与可读性禁令措辞、
   正文无裸 `$`；YAML 与 prompt_version 对应。

**验收（用户侧）**：真实 LLM 联调观察——`analysis` 是否仍出现英文字段泄漏
与定级矛盾；统计 `analysis_polish` 分布确认润色实际生效率（`failed` 占比
偏高说明润色 Prompt 输出格式不稳，需加强约束）。列为发版观察点。
