# DriveIntent V1.1 设计文档

**文档版本：** 1.0
**日期：** 2026-07-27
**状态：** 已评审通过
**上游文档：** `claude_docs/2026-07-23-v1-design.md`（V1.0 设计）

------

## 1. 目标与范围

V1.1 在 V1.0 基础上解决三个问题：

1. **filter_type 字段**：Agent 1（评论价值初筛）输出中新增 `filter_type`，标识评论内容类型（真实用户 / 车主 / 水军 / 营销号等），供前端筛选与核查。所有评论（含通过初筛的）均返回该字段。
2. **车主评论过滤**：识别"已购车"与"已下大定"的车主评论，此类评论暂无营销价值，予以过滤（两类分别用独立的 filter_type 值标识）。
3. **非我方车型的意向降级**：视频目标车型与我方在售主力车型差异过大（价位、品类）时，对评论的意向等级降级。为此新增"我方在售主力车型"配置项（多款车型），并提供文本描述 → 结构化配置的 LLM 转换脚本。

### 1.1 核心决策

| 决策项 | 结论 |
|---|---|
| filter_type 输出范围 | 所有评论都返回，通过初筛的为 `genuine_user` |
| 车主分类粒度 | 已购（`existing_owner`）与已大定（`ordered_owner`）分为两个值 |
| 降级执行方式 | 评论筛选 Skill 输出原始判断，代码层规则后处理（流程解耦），直接覆盖 `intent_strength` |
| 降级贯穿范围 | Agent 1 规则降级 `intent_strength` 并在 API 输出暴露；Agent 2 Prompt 注入我方车型信息，由 LLM 综合考量 |
| 我方车型判定 | 视频语境的 brand/model 与配置做别名匹配；命中我方车型则跳过全部后处理 |
| 配置存放 | JSON 配置文件 `config/our_models.json`，`.env` 配路径，重启生效 |
| filter_reason 枚举 | 在 V1.0 四个值基础上扩展（已与下游确认可扩展） |

### 1.2 明确不做

- 不改 API 异步作业机制（`api_job` 表、`ApiJobWorker`、轮询契约不变）。
- 不做配置的数据库存储与管理 API（车型变化频率低，文件配置足够）。
- Agent 2 不做代码层强制降级（账号评论历史跨多视频多车型，规则化易失真）。
- 不改 V0 流水线路径（8000 测试链路）的 lead 生成逻辑。

## 2. 总体架构

V1.1 为增量叠加，新增独立模块 `app/matching/`，单一职责：我方车型匹配度评估。

```
app/matching/
├── models.py       # OurModel 配置数据结构（Pydantic）
├── loader.py       # 加载 config/our_models.json + 缓存
└── downgrade.py    # 匹配度计算 + 降级规则（纯函数，无 IO）
```

Agent 1 处理流程（【】为 V1.1 新增）：

```
视频分组
  ↓
视频语境 Skill（【新增输出 price_range / vehicle_category / powertrain / use_case】）
  ↓
【our_models 匹配判定 → is_our_model?】
  ↓
评论筛选 Skill（【新增输出 owner_status / comment_actor】）
  ↓
【后处理：is_our_model=true → 跳过降级；
         is_our_model=false → 按匹配度降 intent_strength】
  ↓
边界映射 → API 输出（【新增 filter_type / intent_strength / downgrade_* 字段】）
```

`downgrade.py` 为**纯函数**：输入（视频语境、我方车型列表、原始 intent_strength）→ 输出（降级后 intent_strength + 降级理由）。不依赖 LLM 与数据库，可独立单元测试。

Agent 2 变化较轻：用户分析 Prompt 注入我方车型摘要文本，LLM 评定 H/A/B/C 时把"品牌匹配度"作为考量维度。

## 3. 主力车型配置与转换脚本

### 3.1 配置结构 `config/our_models.json`

```json
{
  "version": "1.0",
  "updated_at": "2026-07-27",
  "models": [
    {
      "model_id": "xxx-01",
      "brand": "某品牌",
      "model_name": "某车型",
      "aliases": ["车型简称", "内部代号"],
      "price_min": 350000,
      "price_max": 420000,
      "vehicle_category": "SUV",
      "powertrain": "PHEV",
      "use_case": ["越野", "家用"],
      "key_features": ["四驱", "大空间", "智驾"],
      "target_audience": "30-45岁男性，户外爱好者"
    }
  ]
}
```

`aliases` 是匹配关键——视频语境提取的车型名常为简称或口语化说法，靠别名列表提高命中率。价格单位为元。

### 3.2 转换脚本 `scripts/build_our_models.py`

读入自由文本描述（车型介绍、配置单等），调用 LLM 抽取为上述结构，写入配置文件。

```
python scripts/build_our_models.py --input docs/our_models.txt
python scripts/build_our_models.py --input docs/our_models.txt --dry-run
```

- 复用现有 LLM Gateway，不新增依赖。
- 输出前 Pydantic 校验，校验失败直接报错退出，不写坏文件。
- 写盘前若目标文件已存在，先备份为 `our_models.json.bak`。
- `--dry-run` 只打印结构供人工核对，不写盘。

### 3.3 匹配判定（三级）

视频语境的 `brand` + `model` 与配置匹配（忽略大小写、去空格）：

1. `model_name` 或 `aliases` 精确命中 → `is_our_model=true`，跳过全部降级。
2. 仅 `brand` 命中（我方品牌其他车型）→ 不降级（同品牌用户仍有价值）。
3. 都不命中 → 进入降级评估（见第 5 节）。

### 3.4 配置项（.env 新增）

```
OUR_MODELS_CONFIG_PATH=config/our_models.json
INTENT_DOWNGRADE_ENABLED=true
```

- `INTENT_DOWNGRADE_ENABLED=false`：完全跳过降级逻辑，作为快速回退开关。
- 配置文件缺失或解析失败：记录警告，自动跳过降级，不使整单失败。

## 4. filter_type 分类与车主识别

### 4.1 内部 Skill 输出扩展

`CommentScreeningItem` 新增两个正交字段：

```python
owner_status: Literal["none", "existing_owner", "ordered_owner"] = "none"
comment_actor: Literal["genuine_user", "bot_spam", "marketing_account",
                       "noise", "off_topic"] = "genuine_user"
```

拆两个字段而非让 LLM 直接输出单一 filter_type：一条评论可能既是"营销号"又带"车主特征"，分别判断再由代码合成，比 LLM 七选一更稳定。

### 4.2 filter_type 合成优先级（`mapping.py`）

```
1. off_topic          — 与汽车无关（最先排除）
2. noise              — 无实质内容
3. bot_spam           — 水军刷屏
4. marketing_account  — 营销号引流（优先于车主：伪装成车主的营销号归营销号）
5. existing_owner     — 已购车主
6. ordered_owner      — 已大定车主
7. genuine_user       — 以上都不是
```

### 4.3 passed 与 filter_reason 映射

```python
passed = filter_type == "genuine_user"
```

| filter_type | filter_reason |
|---|---|
| `genuine_user` | `null` |
| `existing_owner` | `已购车主评论` |
| `ordered_owner` | `已下定车主评论` |
| `bot_spam` | `批量刷屏水军` |
| `marketing_account` | `广告/引流类评论` |
| `noise` | `无实质内容` |
| `off_topic` | `与汽车无关` |

（V1.0 枚举中的 `重复内容评论` 保留定义但由 `bot_spam` 路径覆盖。）

### 4.4 Prompt 增补（`comment_lead_screening_v1.txt` → v2 新文件）

车主识别判断依据：

- 已购信号：提车、已开了 X 公里、我的车、保养经历、用车体验陈述、车机使用感受。
- 已大定信号：已下定、交了定金、等提车、排产、锁单。
- **反例强调**：「准备订」「想下定」「打算买」是意向不是已购，不得判为车主。
- 咨询他人用车体验（如「车主们保养贵吗」）是潜在买家，不是车主。

保留 v1 Prompt 文件，新增 v2，yaml 切换 `prompt_file`，便于回退对比。

## 5. 意向降级规则

### 5.1 视频语境 Skill 扩展

`VideoContextResult` 新增（LLM 依据车型常识估算，取不到留 null）：

```python
price_range_min: int | None = None      # 单位：元
price_range_max: int | None = None
vehicle_category: str | None = None     # 轿车 / SUV / MPV / 越野 / 皮卡 等
powertrain: str | None = None           # 燃油 / 纯电 / PHEV / HEV
use_case: list[str] = []                # 家用 / 越野 / 通勤 / 商务
```

对应 Prompt `video_context_analysis_v1.txt` → v2 新文件。

### 5.2 匹配度计算（`downgrade.py` 纯函数）

两个维度独立判定，"不匹配维度数"决定降级档位：

- **价格维度**：取视频车型价位中值（`(price_range_min + price_range_max) / 2`）与我方车型价位中值（`(price_min + price_max) / 2`）之比，比值在 `[0.7, 1.4]` 内算匹配。多款我方车型取**最宽松**结果（任一款匹配即算匹配）。
- **品类维度**：`vehicle_category` 或 `use_case` 与我方任一车型有交集即匹配。SUV 与越野视为相近品类，不算不匹配。

```
不匹配数 = 0 → 不降级
不匹配数 = 1 → 降一级
不匹配数 = 2 → 降两级
```

降级阶梯：`high → medium → low → none`，降到 `none` 为止不越界。

**信息缺失保守策略**：价位或品类任一维度取不到值（null），该维度不计入不匹配——宁可漏降级也不错降级，避免 LLM 未估出价位时误杀有效线索。

### 5.3 Agent 2 的改动

`user_lead_analysis` Prompt（v1 → v2 新文件）注入我方车型摘要（品牌、车型、价位、品类、目标人群），要求 LLM 评定等级时把"该用户与我方车型的匹配度"作为考量维度之一。不做代码层强制降级。

## 6. API 输出扩展

`ScreeningResult` 新增字段（对接文档需同步更新）：

```python
filter_type: str = "genuine_user"
intent_strength: str = "none"           # 暴露内部意向强度（降级后值）
downgrade_applied: bool = False         # 是否发生降级
downgrade_reason: str | None = None     # 降级原因说明（供前端核查与规则调优）
```

`ProfileResult` 结构不变（Agent 2 的匹配度考量体现在 LLM 产出的等级与分析文本中）。

## 8. 错误处理汇总

| 异常 | 处理 |
|---|---|
| our_models.json 缺失/解析失败 | 警告日志，跳过降级，不使整单失败 |
| INTENT_DOWNGRADE_ENABLED=false | 完全跳过匹配与降级 |
| 视频语境价位/品类为 null | 该维度不计入不匹配（保守） |
| 转换脚本 LLM 输出校验失败 | 报错退出，不写盘 |
| 转换脚本覆盖已有配置 | 先备份 .bak 再写 |
| LLM 输出的 owner_status/comment_actor 非法值 | Pydantic 校验触发批次重试（沿用 V1.0 机制） |

## 9. 测试

### 9.1 单元测试（不依赖 LLM）

**downgrade.py（纯函数，重点覆盖）**：
- 同价位同品类 → 不降级
- 单维度不匹配 → 降一级
- 双维度不匹配 → 降两级
- 价位/品类缺失 → 该维度不计不匹配
- 我方车型命中 → 跳过降级
- 仅品牌命中（同品牌其他车型）→ 不降级
- 多我方车型取最宽松匹配
- 降级不越界（none 不再降）
- 开关关闭 / 配置缺失 → 跳过

**mapping.py**：
- filter_type 七个值的合成优先级
- 营销号 + 车主特征同时命中 → 归营销号
- passed 仅在 genuine_user 时为 true
- filter_reason 新枚举映射

**loader.py**：配置解析、别名归一化（大小写/空格）、缺失文件降级。

**转换脚本**：MockProvider 下抽取 → 校验 → dry-run / 写盘 / 备份行为。

### 9.2 集成测试（MockProvider）

- 带降级的 comment-screening job 全流程：提交 → 轮询 success → 校验新字段。
- 我方车型视频的 job：全程无降级。
- Agent 2 job：Prompt 含我方车型摘要（Mock 断言输入）。

### 9.3 真实模型联调（实现阶段最后）

- 用真实车型描述跑转换脚本，人工核对结构。
- 真实评论子集跑 Agent 1，重点核查车主识别的误判率（意向誤判为已购）与降级合理性。

## 10. 与 V1.0 的关系

- API 契约向后兼容：仅新增输出字段与 filter_reason 枚举值，不改既有字段语义（`intent_strength` 从内部字段变为对外暴露）。
- `api_job`、Worker、认证、轮询机制零改动。
- 三个 Skill 均以 v2 Prompt 文件叠加，v1 保留可回退。
- 对接文档 `docs/DriveIntent-V1-API对接文档.md` 需同步更新新字段与新枚举。
